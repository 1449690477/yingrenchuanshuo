## Context

当前 `src/save/storage.ts` 已实现主/备份槽、Zod 迁移校验、写队列和 IndexedDB revision/CAS。它解决的是可靠性与并发，不是对抗性篡改：revision 和存档内容都在同一个客户端数据库里，攻击者可以一起修改；任何写在 JavaScript 包里的 HMAC 密钥也都能被读取。

因此本变更采用两层模型。L1 是“篡改可见和可恢复”，主要保护普通玩家免受损坏、扩展误写与随手编辑；L2 是“联机资产权威”，才负责阻止伪造装备进入排行榜、公会和未来交易。

## Goals / Non-Goals

**Goals:**

- 让主存档、备份与 revision 形成可验证的单调链，异常不再与普通坏档混为一谈。
- 旧 v12 裸快照无损读取，首次写入升级物理信封且不触发 SaveData 迁移。
- JSON 导入导出继续可用，并清楚表达“可玩”不等于“联网可信”。
- 定义服务端权威资产最小账本，为后续公会奖励和交易提供硬边界。

**Non-Goals:**

- 不声称客户端摘要、WebCrypto 或代码混淆能阻止高级篡改。
- 本变更第一阶段不把全部挂机 tick 搬到服务端，也不要求持续联网。
- 不在同一提交开放装备交易、公会战力奖励或付费经济。

## Decisions

### 1. 物理信封与 SaveData 版本分离

IndexedDB 槽位保存 `{ envelopeVersion, revision, parentDigest, digest, writtenAt, source, payload }`。`digest` 对稳定序列化后的元数据和 payload 使用 SHA-256；摘要不含自身。业务 `payload.version` 仍为 `SAVE_VERSION=12`，因为业务结构未变。

### 2. 不使用客户端秘密制造虚假安全

L1 使用公开摘要而不是内置 HMAC 密钥。公开摘要能发现偶发损坏和只改 payload 的低成本编辑，但攻击者可以重算。UI 和文档必须称其为“完整性检测”，不能称为服务端防作弊。

### 3. 异常优先恢复，不自动销毁

主槽校验失败而备份链合法时，提示玩家恢复备份；两者都异常时允许导出原始数据供排查并提供明确清档选择。系统不得静默把异常档覆盖成新档，也不得上传联机成绩。

### 4. 导入档保持本地可玩，但不继承联网可信度

JSON 只导出/导入 `SaveData`，不会导出服务端证明。导入成功后建立 `source=imported` 的新本地链；单机功能照常，联网关键资产必须重新与服务端账本对账。

### 5. 服务端账本只收事件，不收客户端余额

L2 使用 `asset_accounts`、`asset_items`、`asset_events` 和 `asset_requests`。客户端提交操作意图及幂等 ID，服务端在事务中验证来源、余额、装备 UID 和前置 revision，再写事件与新快照；客户端不得上报最终金币、材料总量或“已获得装备”。

### 6. 离线收益通过待兑换凭证进入联机经济

离线期间仍可本地挂机。需要进入公会奖励、交易或竞争玩法的新增资产，必须通过服务端可复算的时间窗/种子凭证兑换；无法证明的导入资产保留单机使用，但不进入联机权威库存。具体兑换上限和补偿体验在 L2 实施前单独做数值决策。

## Risks / Trade-offs

- L1 会增加每次保存一次 SHA-256 和稳定序列化成本；需要测量 300 件背包及低端手机，必要时在写队列异步执行。
- 主/备份链只能看到最近两代，不能提供完整审计历史；完整事件历史只放服务端。
- L2 会引入 Supabase 成本和断网冲突处理，也会限制任意 JSON 改档后直接参加联机玩法。
- 旧玩家首次升级信封必须绝对无损；任何歧义都应保留原始槽位并停止自动写入。

## Migration Plan

1. 实现稳定序列化、摘要信封与旧裸快照兼容测试。
2. 接入主/备份读取、CAS 写入与完整性异常 UI；不改 SaveData 版本。
3. 在实际 390×844 页面和 300 件背包下验证保存延迟与恢复流程。
4. 单独设计并部署服务端资产账本，再逐项迁移装备奖励、货币和交易。
5. 只有 L2 生产验收后，才开放会影响他人的公会战力奖励或资产流转。

## Open Questions

- 导入档是否永久显示“本地档”标记，还是在一次完整服务端对账后消除？
- 离线挂机资产进入权威账本时采用“服务端复算全部收益”还是“每日有限兑换额度”？
- 玩家主动使用模组/改档的单机体验是否需要单独存档槽，彻底与联机档隔离？
