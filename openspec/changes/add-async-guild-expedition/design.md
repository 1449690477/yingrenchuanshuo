## Context

项目已有 Supabase 匿名身份、档案、周常试炼服务端复算、竞技场原子结算和断网降级，但本地存档仍不是服务端权威数据。公会首版必须复用这些能力建立真实共享状态，又不能让客户端伪造的装备或资源进入可交易经济。

现有 UI 以 390×844 竖屏为基准，“更多”页已经使用全屏子页面承载精品店。公会采用相同的单层页面交接，不新增底部主 Tab，也不把公会窗口叠在其他弹窗之上。

## Goals / Non-Goals

**Goals:**

- 提供真实在线的 20 人公会创建、加入、退出、公告和成员管理闭环。
- 提供不占用挂机角色状态的每周异步首领，以服务端复算结果累加共享进度。
- 让不同等级成员面对同主题、同周规则但按等级分段缩放的首领，并用归一化贡献公平合作。
- 所有成员关系、贡献与公会成长都由数据库原子维护；重复请求不能重复计数。
- Supabase 未配置或断网时不影响任何单机玩法。

**Non-Goals:**

- 不做实时同屏、聊天、好友、申请审批、公会战、领地、交易行或装备交换。
- 不发放装备、金币、材料、战力加成或本地背包奖励。
- 不承诺客户端装备真实获得，只校验装备结构与公式合法；服务端权威存档另行建设。
- 不新增公会技能树。公会等级首版仅解锁徽记和展示文案，避免强公会滚雪球。

## Decisions

### 1. 公会关系使用数据库原子 RPC，战斗贡献使用 Edge Function

`guild_create`、`guild_join`、`guild_leave`、`guild_update_notice`、`guild_remove_member` 由 SQL RPC 在事务内执行，依靠唯一成员约束和行锁保证一个账号只能属于一个公会、成员上限不会超卖。客户端不直接写公会与成员表。

远征挑战使用 `guild-expedition` Edge Function：客户端只提交职业、等级和八槽装备快照，不提交伤害或贡献；服务端复用 `src/core` 构建角色、生成周首领并模拟战斗，再调用原子 RPC 写入当日最好成绩的差值。

替代方案是全部由客户端计算后直接写表，但客户端可任意篡改贡献，不采用。全部塞进 SQL 又无法复用 TypeScript 战斗公式，也不采用。

### 2. 使用“每日最好贡献”，而不是每次伤害直接累加

每名成员每天最多提交三次有效挑战，同一天只有最高贡献计入公会总进度。刷新成绩时，数据库只把新旧最好值的差额加入共享进度；网络重试、相同请求和较低成绩均不会重复增加。

这既允许玩家换装后再试，也避免把公会变成每天机械点击三次的任务。次数按北京时间 04:00 切日，周一 04:00 切周。

### 3. 不同等级使用同主题分段首领，贡献按血量比例归一化

首领名字、元素和倾向由赛季与周次确定；属性和血量按玩家所在试炼分段缩放。纯函数把本次伤害换算为 0～1000 的贡献点，基准搭配完整战斗约得到目标贡献，极端装备也不能突破单次上限。

周目标在该公会本周第一次远征时锁定为 `max(1, 当时成员数) × 每成员目标贡献`。目标按约四个有效参与日设计，新加入成员可以帮忙，但中途退会不会让目标倒退。首版奖励仅为公会声望，允许接受这一轻微的成员变动收益。

### 4. 公会成长只做展示

完成周目标增加一次远征完成数和固定声望；等级由累计声望的纯函数计算，只解锁徽记、边框描述和公会据点阶段。它不进入玩家属性、掉落率、离线时间或排行榜伤害。

这是在服务端权威存档完成前的安全边界，也避免“必须加入高等级公会”成为养成税。

### 5. 共享表和访问边界

新增：

- `guilds`：名称、公告、会长、声望、累计远征完成数。
- `guild_members`：唯一 `user_id`、角色、加入时间和展示快照。
- `guild_expeditions`：公会 + 周唯一，锁定目标、累计贡献与完成状态。
- `guild_contributions`：公会 + 周 + 日 + 用户唯一，保存当日最好贡献、提交次数与搭配哈希。

已认证玩家可以读取公开公会摘要；成员才能读取完整成员和贡献明细。所有写入通过受控 RPC 或 Edge Function，RLS 禁止客户端直接修改核心字段。

### 6. 客户端边界和页面结构

`src/net/guild.ts` 只做 RPC/Function IO 与响应整形；`src/stores/guild.ts` 负责连接状态、缓存和交互状态；规则进入 `src/core/guildExpedition.ts`，参数进入 `src/data/guildRules.ts`。

“更多”页移除“公会即将开放”芯片并增加公会入口。`GuildView.vue` 是单层全屏子页面，包含未加入时的公会列表/创建表单，以及加入后的首页、远征、成员三个页签。页面关闭后焦点返回入口按钮。

## Risks / Trade-offs

- **[合法装备仍可伪造]** → 首版没有战力或可交易奖励；服务端继续做定义、等级、职业、槽位和词条公式硬校验，并在 UI 说明为测试期荣誉玩法。
- **[小公会活跃不足]** → 周目标按首次参与时的成员数锁定，单人公会也能在一周内完成；不按公会最大容量固定。
- **[成员进出利用目标锁定]** → 新成员帮助不会扩大目标，但收益仅为展示声望；若未来加入经济奖励，必须改为成员日配额或动态目标。
- **[匿名账号丢失]** → 沿用现有匿名会话；账号绑定与找回不在本期，但公会页应提示未绑定账号的设备风险。
- **[免费实例或网络暂停]** → 所有请求显式重试、可关闭页面，挂机主循环零依赖；未配置时展示“联机服务未配置”而不是报错堆栈。
- **[Edge Function 与客户端 core 分叉]** → 纳入现有 `npm run edge:build`，增加确定性自检，并在部署文档列出迁移和函数发布顺序。

## Migration Plan

1. 先合并前端、迁移 SQL、Edge Function 与文档；未部署时入口显示联机服务未配置，单机功能不受影响。
2. 在 Supabase 执行公会迁移，再运行 `npm run edge:build` 并部署 `guild-expedition`。
3. 用两个匿名账号验收创建、加入、贡献、退出和会长转移。
4. 若需回滚，先隐藏前端入口并停止部署函数；数据库表保留只读，避免删除公会数据。首版不改本地存档，无存档回滚。

## Open Questions

- 公会聊天和申请审批留到第二期，根据真实公会数量与活跃度决定，不预建空表。
- 后续若引入可领取资源，必须先决定服务端权威存档或沿用竞技场 grant 同步模式，并重新评估重复入包风险。
