# 进度榜（docs/63 §五 · P4，docs/51 §4 榜 3）——开荒者的荣誉

>  deepest_stage_index desc, deepest_stage_at asc **nulls last**。
>  「没有证据就不能主张更早」—— 不是惩罚（docs/62 §4.1 同一口径）。

## 一、这个榜是什么

全服开荒竞速：谁推图推得最深；推到同一深处时，谁先到的。
数据源是存档里的 `clearedStageIds` 与 `stageFirstClearedAt`（存档 v15 起逐关记录，
赶在区域 7 上线前落地，r7 的 30 关每一关都有真实时刻）。

玩家看到的：RankView 第四页签「进度榜」（试炼榜 | 进度榜 | 羁绊榜 | 竞技场）。
上半「开荒长卷」卡展示本地推导的最深首通（不联网也能看），下半「开荒同行榜」
展示全服 verified 行。弱名次口径与羁绊榜一致：小号暗色无奖牌、无皇冠、
行不可点、无查看他人；我自己的回执给「超过 N% 的旅人」而不是精确名次压力。

## 二、三条硬口径（不可偏离）

1. **排序**：最深关卡序号降序；同序号按首通时刻升序；**无时刻的排在有时刻的
   之后**。老档已通关的关卡没有时刻且**不补记** —— 行上写「时刻未记录」，
   不假装知道一个已经丢失的时间。
2. **客户端无权自称任何东西**：上报载荷只有 `{ stageId, firstClearedAt }`。
   序号服务端从白名单推导，名次服务端数出来，verified 服务端判定。
3. **名次不发放任何竞技奖励** —— 先到达这件事本身，就是奖励（页脚原文）。

## 三、数据流

```
game.ts 首通捕获处（clearedStageIds 追加的那一处，全仓唯一）
  → 火忘上报 notifyFirstClear（只在 status==='ready' 的玩家身上自动联网；
    动态 import 避免 game → progressBoard → game 静态环；任何失败吞掉，
    绝不阻塞战斗结算）
开榜（ProgressBoardView onMounted → openBoard）
  → 有未同步进度则 syncProgress（上报 → 立即重拉），否则只拉榜
上报 submit-progress（Edge Function）：
  L1 结构白名单 → L3 同源门槛判定 → L2 原子只升不降 RPC → 数名次
拉榜 fetchProgressBoard：progress_records ⋈ profiles，verified 行内排序取前 50
```

未配置 Supabase / 离线：所有联机动作静默降级，本地推导的开荒卡照常展示。

## 四、反作弊（与速度榜同构：服务端无法复算，防线是结构与判定）

「你何时首通了这一关」是一段已经过去的历史，服务端手里没有任何东西能
重建它。三层防线（claude 2026-07-31 06:30 复核确认全部口径）：

- **L1 结构白名单**：`stageId ∈ ORDERED_STAGE_IDS`；时刻落在
  `[2026-01-01, 服务端时间+5min]` 整数窗口（与副本首通时刻判据同源；
  上界留 5 分钟时钟漂移容差，下界用赛季起点而不是 0）。
- **L2 只升不降（原子 upsert）**：`submit_progress_record` RPC
  （security definer + 行锁）：
  - 新序号更大 → 整行覆盖（更深的首通取代旧的，verified 以新判定为准）；
  - 同序号 → 只允许 ①null→有值补时刻 ②verified false→true 翻正 ——
    后者给「清装备导致战力低于门槛被误标」的合法玩家留恢复路，
    反向 true→false 永不允许（堵洗白）；
  - 序号更小 → 一字不改（另一台设备报过更深，榜上以更深的为准）。
- **L3 verified 软旗标不硬拒**：用与游戏内进入门槛**同一份实现**
  `evaluateChapterGate` 判定（profiles.level 够 legacy-bypass 或
  profiles.combat_power 过该章门槛才 verified；不足则收下但不入榜）。
  伪造一条深进度需要先把 combat_power 垫到门槛之上 —— 那会同时把自己
  挂上战力榜被人看见（成本不对称，submit-milestone 同口径）。
  名次只在 verified 行内排。

### 为什么是专用表 progress_records，不走 profiles 加两列

docs/63 §五 的原始建议是 profiles 加 `deepest_stage_index` + `deepest_stage_at`
两列。实测后撤回：profiles 的 own-row upsert 策略是 **for all**，已登录客户端
可以直接 PATCH 自己那行的任何列（claude 06:30 用匿名 key + 策略文本双侧验证）。
竞速榜挂 profiles 等于把名次开放给客户端自填。专用表 RLS 全员只读、
**没有任何写策略**、只有 service role 经 RPC 写 —— 照 milestones /
dungeon_records 先例。（注：claude-dungeon 提醒过「列级 revoke 削不掉表级
授权」的陷阱 —— 这里根本不靠列级权限，整张表客户端只读。）
