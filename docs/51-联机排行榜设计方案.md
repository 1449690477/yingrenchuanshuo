# 51 · 联机排行榜设计方案（Supabase）

> 所有者需求：接入 Supabase 做后端让玩家联机，排行榜「除了当前进度和战斗力，
> 不知道还要展示什么」，希望它能让玩家**不断追赶、喜欢这个游戏**。
>
> 本文档是给实施者（kimi）的完整方案。数值与机制由 claude 负责。
> 设计透镜与红线沿用 [`40-玩法设计透镜.md`](40-玩法设计透镜.md)。

---

## 零、先说一句不好听的

需求里的「上瘾」有两种做法，一种**在本项目里被明令禁止**：

`40-玩法设计透镜.md` 第三节红线清单写得很清楚 ——
「社交攀比式提醒」属于**焦虑**类禁止项，并且第二节点名过：

> ❌ 排行榜若引入，不做「掉出前 N 名」的羞辱式提示。

所以「你被超越了，快上线」这条路不走。**这不只是道德洁癖，它在放置品类里根本无效**：
放置游戏玩家大部分时间不在线，用焦虑驱动只会把「自愿参与」变成「义务」，
而自愿参与是麦戈尼格尔定义里**游戏与苦工的分界线**。玩家不会更努力，只会卸载。

本文档给的是另一条路：**让玩家有东西可追、追得到、追到了有人看见。**

---

## 一、为什么「纯战力榜」一定会失败

这不是风格问题，是结构问题。放置游戏的战力有三个特点：

### 1.1 战力 ≈ 玩了多久

战力主要由等级和装备决定，而两者都随挂机时间单调增长。
结论：**先玩的人永远在前面**。三个月前入坑的玩家，新玩家永远追不上。

新玩家打开排行榜看到的是一堵**够不到的墙** —— 直接击穿自我决定论里的
**胜任感**（「我在变强，而且我知道为什么」）。他不会想追，他会关掉。

### 1.2 单榜 = 99% 的人是失败者

全服一个榜，只有前 100 名有感觉。**对第 3000 名来说，
排行榜的唯一功能是每天提醒他「你不是谁」。**

### 1.3 战力衡量的是「积累」，不是「决策」

这是最致命的一条。挂机产出是**游戏给的**，不是玩家**选的**。
给积累发奖，等于表彰玩家「挂了很久」——
对照 doc 40 自检表第 7 问：**它增加的是决策还是点击？** 纯战力榜两个都不是。

> **本方案的核心转向：把排行榜从「谁挂得久」改成「谁搭得好」。**

---

## 二、设计目标与硬约束

| 目标 | 手段 |
|---|---|
| 人人都能是某方面第一 | 多榜 × 职业分榜 × 等级分段 |
| 消除时长优势 | 周常重置 + 效率类指标 |
| 比的是决策不是积累 | 固定种子试炼（核心机制，见第三节） |
| 看得见的是身边的人 | 邻域榜（你 ±5 名）优先于全服前 100 |
| 不上线也不损失 | 榜单只记录最好成绩，**永不倒退、永不清空已得奖励** |

**硬约束（违反即打回）**

- ❌ 不做「你被 XXX 超越了」推送
- ❌ 不做掉名提示、不做名次下降动画
- ❌ 不做「本周不参与则失去上周段位」
- ❌ 排行榜奖励**不得含战力**（否则强者愈强，墙更高）→ 只给外观、称号、
  收藏品、少量通用材料
- ✅ 赛季结束时展示的是**你的最好成绩**与**你比上赛季进步了多少**，
  不是「你掉了多少名」（峰终法则：终必须是正面的）

## 三、核心机制：周常试炼（固定种子 Boss）

**这是整个方案里唯一真正重要的东西，其余榜单都是围绕它的补充。**

### 3.1 是什么

每周全服面对**同一个 Boss、同一个随机种子**。玩家用自己当前的搭配挑战，
记录 **60 秒内造成的总伤害**。周一 04:00（沿用游戏既有日切）重置。

### 3.2 为什么这个机制对本项目是最优解

| 理由 | 说明 |
|---|---|
| **它比的是搭配，不是时长** | 同级同职业下，Boss 完全相同，差距只来自装备、词条、强化、技能的选择 |
| **它给了洗练系统一个目的** | 我们刚做完词条洗练（docs/43、48），但玩家「洗到什么程度算够」没有答案。试炼榜就是那把尺子 |
| **服务端可以复算验真** | `src/core/` 完全纯净（无 Vue/Pinia/存储），`Rng` 是确定性 PRNG，`simulateFight` 是纯函数 —— Edge Function 能用**同一份代码**重跑这场战斗。见第六节 |
| **每周清零，没有墙** | 老玩家的优势只剩「装备更好」，而不是「领先三个月的累积名次」 |
| **它造「峰」** | 放置游戏中段必然平淡（doc 40 第二节峰终），每周一次的冲榜是天然的峰 |
| **它有明确的 Fiero** | 「我把伤害从 12 万提到 15 万」是具体的、可讲给别人听的胜利 |

### 3.3 用伤害而不是「通关时间」

**不设失败状态。** 所有人都能打出一个数字，永远有分可比、有分可涨。
如果用「击杀耗时」，打不过的人直接出局 —— 那正是 1.2 节的问题。

伤害是**连续指标**，任何一点搭配改善都能立刻在数字上看见 ——
这就是自我决定论的**胜任感**：我在变强，而且我知道是因为什么。

### 3.4 分段：让低级玩家也有得比

| 分段 | 等级区间 |
|---|---|
| 初樱 | 1 – 30 |
| 绯月 | 31 – 60 |
| 琥珀 | 61 – 90 |
| 绯樱 | 91 – 120 |

Boss 在每个分段内**完全相同**（属性由分段 + 周种子生成）。

叠加职业分榜后共 **4 分段 × 4 职业 = 16 个子榜**，每周产生 16 个第一名，
外加一个全服总榜。**「我是本周绯月剑姬第一」是够得着的目标。**

### 3.5 Boss 生成规则

```
seed = hash(seasonId, weekIndex, bracketId)
```

Boss 属性以该分段**中位等级的满配玩家**为基准（复用
`src/data/expectedPower.ts` 的 `expectedFullGearCp`，见 docs/47），
HP 设为足够高使 60 秒内**打不完**——保证指标是「伤害」而非「剩余时间」。

每周附带一个**词条倾向**（如「本周 Boss 减伤很高，破防词条更有价值」），
让最优解每周变化 → 多变的酬赏（Hooked 模型），也避免一套配装吃一年。

## 四、榜单矩阵

| # | 榜名 | 指标 | 周期 | 解决什么 |
|---|---|---|---|---|
| 1 | **周常试炼榜** | 60 秒总伤害 | 每周 | 核心竞技，比决策 |
| 2 | 战力榜 | 当前战力 | 赛季 | 传统需求，保留但**不作主推** |
| 3 | 进度榜 | 最深通关关卡，同关按最早达成排 | 赛季 | 开荒者的荣誉 |
| 4 | **登顶速度榜** | 从创号到首次达成 Lv50/80/110 的**用时** | 常驻 | **完全消除时长优势**，新玩家与老玩家同起点 |
| 5 | 秘境榜 | 装备副本各档最快通关 | 赛季 | 给副本一个上限追求 |
| 6 | 鉴藏榜 | 图鉴收集度（装备种类 + 奇遇 + 好感） | 常驻 | 给非战斗玩家的赛道 |
| 7 | 羁绊榜 | 好感总进度 | 常驻 | galgame 线玩家的赛道 |

**主推顺序**：1 > 4 > 3 > 其余。战力榜放在次级页签，
因为它是玩家**期待看到**的，但不是我们**希望他追**的。

> 榜 4「登顶速度榜」值得单独强调：它衡量的是「你用多少天到达 Lv50」，
> 今天入坑的新人和一年前的老玩家**在同一条起跑线上**。
> 这是整个方案里唯一能让新玩家「一入坑就能上榜」的机制。

## 五、反墙机制（比榜单本身更重要）

### 5.1 邻域榜优先

打开排行榜，**默认视图不是前 100，而是「你 ±5 名」**。

理由：全服第 3000 名看到第 2998 名只领先他 2% 伤害，是**够得着的目标**；
看到第 1 名领先他 40 倍，只会关掉。

前 100 作为单独页签保留 —— 它是「远景」，不是「日常目标」。

### 5.2 段位而非精确名次

对榜单中后段，展示**段位徽章**（如「绯月·上位 20%」）而不是「第 3271 名」。

精确名次对第 3271 名是噪音；百分位是他能理解、能追的信号。
**前 100 名内才显示精确名次**（那时精确名次本身就是荣誉）。

### 5.3 个人最好成绩恒久展示

每个榜单页首先显示**你自己的最好成绩和它的变化**：

```
本周试炼    14.2 万伤害    ↑ 比上周 +18%
```

**注意箭头只在上升时出现。下降不显示箭头、不显示红色。**
（doc 40：进度条倒退属禁止项）

### 5.4 奖励只发外观与收藏

| 名次 | 奖励 |
|---|---|
| 分榜前 3 | 限定称号（含赛季名，永久保留）+ 头像框 |
| 分榜前 10% | 称号 |
| 参与即得 | 少量通用材料（洗练石等），**不含战力** |

**参与即得**这一档很关键：它保证「打了就有收获」，
不会出现「冲榜失败一无所有」——那会踩到惩罚性红线。

## 六、Supabase 实现

### 6.1 表结构

```sql
-- 玩家公开档案（一人一行）
create table public.profiles (
  id            uuid primary key references auth.users on delete cascade,
  display_name  text not null check (char_length(display_name) between 1 and 20),
  class_id      text not null check (class_id in ('swordsman','witch','shaman','catkin')),
  level         int  not null check (level between 1 and 120),
  combat_power  bigint not null default 0,
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);

-- 赛季
create table public.seasons (
  id          text primary key,           -- 's1'
  starts_at   timestamptz not null,
  ends_at     timestamptz not null
);

-- 周常试炼成绩（每人每周每分段一行，保留最好）
create table public.trial_scores (
  id           bigserial primary key,
  user_id      uuid not null references public.profiles(id) on delete cascade,
  season_id    text not null references public.seasons(id),
  week_index   int  not null,
  bracket_id   text not null,             -- 'chuying' | 'feiyue' | ...
  class_id     text not null,
  damage       bigint not null check (damage >= 0),
  build_hash   text not null,             -- 提交搭配的哈希，便于查重与复现
  verified     boolean not null default false,
  created_at   timestamptz not null default now(),
  unique (user_id, season_id, week_index)
);

create index on public.trial_scores (season_id, week_index, bracket_id, class_id, damage desc);

-- 里程碑用时（登顶速度榜）
create table public.milestones (
  user_id      uuid not null references public.profiles(id) on delete cascade,
  milestone    int  not null,             -- 50 / 80 / 110
  elapsed_ms   bigint not null check (elapsed_ms > 0),
  verified     boolean not null default false,
  primary key (user_id, milestone)
);
```

### 6.2 RLS（必须开，且必须这样开）

```sql
alter table public.profiles     enable row level security;
alter table public.trial_scores enable row level security;
alter table public.milestones   enable row level security;

-- 所有人可读（排行榜是公开的）
create policy "profiles readable"     on public.profiles     for select using (true);
create policy "trial readable"        on public.trial_scores for select using (true);

-- 只能写自己的档案
create policy "own profile upsert" on public.profiles
  for all using (auth.uid() = id) with check (auth.uid() = id);
```

**成绩表不给客户端 insert 权限。** 客户端只能调用 Edge Function 提交；
函数用 service role 写入。理由见下。

### 6.3 反作弊：服务端复算（本项目的独门优势）

**绝不能信任客户端提交的伤害数字。** 但本项目有个别人没有的条件：

- `src/core/` 完全纯净，不依赖 Vue / Pinia / 存储
- `Rng` 是确定性 PRNG，`simulateFight(stats, monster, rng)` 是纯函数
- 存档已有 Zod schema（`equipmentInstanceSchema`）做结构与取值校验

于是验证流程可以是：

```
客户端提交：{ 职业, 等级, 装备实例快照, 赛季, 周次 }   ← 不提交伤害
                 ↓
Edge Function（Deno，直接 import 同一份 src/core/）
  1. 用 equipmentInstanceSchema 校验每件装备结构合法
     （强化 ≤15、词条数 ≤ 品质允许、品阶 ≤5、数值在 affixValueRange 内）
  2. 由分段 + 周次算出 Boss 与种子
  3. 跑 simulateFight，服务端自己算出伤害
  4. 写入 trial_scores（damage 由服务端产生，verified = true）
```

**伤害由服务端算，客户端根本没有机会伪造它。** 这是这套设计最大的价值。

#### 威胁模型要说实话

上面的方案挡住了「改伤害数字」，但**挡不住「伪造一身合法但没真正获得的装备」**——
因为进度仍在客户端。要彻底解决需要**服务端权威存档**，那是另一个量级的工程。

务实分级，建议按此落地：

| 层级 | 手段 | 本期是否做 |
|---|---|---|
| L1 | 服务端复算伤害 | ✅ 必做 |
| L2 | 装备结构与取值 schema 校验 | ✅ 必做 |
| L3 | 合理性上界：战力不得超过 `expectedFullGearCp(等级) × 1.6` | ✅ 必做，超出标记待审 |
| L4 | 账号年龄合理性：创号 3 天不可能 Lv110 | ✅ 必做 |
| L5 | 服务端权威存档 | ❌ 后续阶段 |

L3/L4 不封号，只标 `verified = false` 并**移出榜单展示**，避免误伤。

### 6.4 匿名登录

放置游戏不该在第一屏要求注册。用 Supabase **匿名登录**（`signInAnonymously`），
玩家想上榜时再引导绑定邮箱做账号找回。**不绑定也能玩，这是自主性。**

## 七、客户端接入点

严格遵守架构铁律：**`src/core/` 不得引入网络**。

```
src/net/supabase.ts        客户端单例
src/net/leaderboard.ts     提交与拉取（纯 IO，不含规则）
src/stores/leaderboard.ts  Pinia store，负责缓存与状态
src/views/RankView.vue     UI
```

- 提交时机：**玩家主动点「提交成绩」**，不做自动上传（隐私 + 自主性）
- 离线可玩：所有网络失败都必须静默降级，**绝不能阻塞游戏主流程**
- 缓存：榜单拉取结果缓存 5 分钟，避免每次切页签都打请求

## 十、验收标准

| 检查项 | 目标 |
|---|---|
| 客户端提交伤害数字 | **必须不可能** —— 伤害只由服务端产生 |
| 断网 / Supabase 故障 | 游戏主流程完全不受影响 |
| 新建账号首次打开排行榜 | 能在 3 秒内找到一个「够得着的目标」 |
| 任一榜单出现「掉名」提示 | **必须为 0** |
| 排行榜奖励含战力 | **必须为 0** |
| 单屏立即决策数 | ≤ 3（doc 40 选择负担） |

| # | 问题 | 回答 |

| 9 | 同屏决策数？ | 1 |
| 10 | 峰在哪？终在哪？ | 峰 = 冲榜刷新纪录；终 = 赛季结算展示**你的进步** |
| 11 | 不玩损失什么？ | **什么都不损失** —— 已得称号永久，无断榜惩罚 |
| 12 | 踩红线了吗？ | 无。焦虑与羞辱类机制已在第二节显式排除 |

## 十一点五、接入准备（所有者要做的 / kimi 要做的）

### A. 所有者在 Supabase 网页上做（约 10 分钟）

2. **打开匿名登录**：Authentication → Sign In / Providers →
   启用 **Anonymous sign-ins**。

   - `Project URL`
   - `anon` / `public` key

4. **把这两个值配到 GitHub**：仓库 Settings → Secrets and variables →
   Actions → New repository secret，建两个：
   - `VITE_SUPABASE_URL`
   - `VITE_SUPABASE_ANON_KEY`

5. 本地开发若要联调，复制 `.env.example` 为 `.env.local` 填同样两个值。
   `.env.local` 已在 `.gitignore` 里。

> **关于 key 的安全，一次说清楚：**
> - `anon` key **可以公开**，它本来就会被打进网页包让所有玩家看到。
>   安全性由 RLS 策略保证，不是靠藏它。
> - `service_role` key **拥有绕过 RLS 的完全权限**，它只属于服务端，
>   由 Supabase 平台自己注入 Edge Function。
>   **永远不要写进本项目任何文件、不要贴进聊天室、不要发给任何 AI。**
>   kimi 部署 Edge Function 用自己的 `supabase login`，不需要这个 key。

## 附录 A · 玩家自定义身份（昵称 / 简介 / 头像）

> 所有者决策（2026-07-29）：昵称由玩家自填、**不要求全服唯一**；
> 头像**允许自由上传**，但必须带防护。
> 数据库层已由 `supabase/migrations/20260729210000_profile_identity.sql` 落地。

### A.1 为什么匿名登录不能省

所有者一度提出「不开匿名登录也行」。不行 —— 它不是「名字来源」，是**身份来源**：

- `signInAnonymously()` 拿到的 `user.id` 就是 `profiles` 表主键
- RLS 判断「这行是不是你的」靠的是 `auth.uid() = id`
- 成绩、头像路径、举报都锚在这个 id 上

**没有它就没有任何身份**，自定义昵称、简介、头像全都无处存放。

### A.2 字段

| 字段 | 限制 | 理由 |
|---|---|---|
| `display_name` | 1~20 字，**不唯一** | 允许重名，改名零摩擦；靠头像与成绩区分 |
| `bio` | ≤ 60 字 | 榜单卡片一行放得下，也压缩辱骂长文的空间 |
| `avatar_url` | 必须指向本项目 avatars 桶 | 禁止外链：外链会被换成违规图，且带 referer 追踪 |

### A.3 头像防护（四层，缺一不可）

| 层 | 手段 | 在哪实现 |
|---|---|---|
| 1 | **桶级硬限制**：≤200KB、仅 jpeg/png/webp | 已在迁移里写进 `storage.buckets`，客户端绕不过 |
| 2 | **路径隔离**：只能写 `avatars/<自己的 uid>/`，无法覆盖他人 | Storage RLS policy |
| 3 | **客户端预压**：上传前压到 512×512、转 webp | **待实现（kimi）** |
| 4 | **举报 + 人工处置** | 表已建；UI 与后台入口**待实现** |

> ⚠ 第 3、4 层还没做。**只做完 1、2 就上线自由上传是不负责任的** ——
> 桶限制只挡住体积和格式，挡不住内容。

### A.4 待 kimi 实现

1. **档案编辑面板**：昵称、简介、头像三项，进入排行榜时若无档案则引导创建
2. **`upsertProfile` 改造**：`src/net/leaderboard.ts:82` 目前把游戏角色名写进
   `display_name`，要改成读玩家自设值；游戏角色名与榜单昵称从此**解耦**
3. **头像上传**：`canvas` 预压到 512×512 → `toBlob('image/webp', 0.85)` →
   上传到 `avatars/<uid>/avatar.webp`（固定文件名，天然覆盖式，不会堆垃圾）
4. **举报按钮**：榜单条目长按或菜单里出现，写 `profile_reports`
5. **降级**：头像加载失败或为空时回落到职业默认图，**不要显示裂图**

### A.5 所有者需要知道的运营成本

自由上传意味着**你要亲自处理举报**。Supabase 免费版没有任何自动审核，
出现违规图时只有你能删（用 service_role 或直接在 Storage 面板删文件 +
清掉 `profiles.avatar_url`）。

另外 Supabase 面板自己也提示过：匿名登录建议配 captcha，
否则可能被刷注册、撑大数据库并推高 MAU 计费。
**目前没配** —— 玩家规模起来之前问题不大，但值得记一笔。
