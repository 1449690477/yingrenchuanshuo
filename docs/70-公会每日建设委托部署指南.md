# 70 · 公会协作大版本部署指南

> 本文用于上线“日建设 + 异步团本 + 服务端功勋 + 赛季据点 + 收藏商店”。
> 它建立在已上线的公会、异步远征和 sync-profile 服务端档案同步之上；
> 不替代、不放宽既有的战力校验，也不把本地背包材料接入联机经济。

## 上线内容与安全边界

- 每天北京时间 04:00 刷新三档远征建设委托；满额建设只增加展示声望与赛季据点进度。
- 既有异步远征在 UI 中显示为“公会团本”：伤害、评分和每日最佳差额仍由 guild-expedition 复算。
- 服务器根据已落库的新增贡献发放“公会功勋”；余额、获得、消费、领取与来源账均在 Supabase。
- 成员可捐献固定的 1 / 5 / 10 点功勋推进赛季据点，也可按固定服务器价格领取本季收藏。
- 收藏不写入本地背包，不发装备、货币、材料、战力、掉率或挂机收益；完整权威资产账本生产验收前不得扩展为资源商店。

## 生产部署顺序

在仓库根目录依次执行：

    npm ci
    npm run edge:build
    supabase db push
    supabase functions deploy guild-expedition

若生产项目不用 Supabase CLI 管理迁移，请在 Dashboard → SQL Editor **按以下顺序**执行：

1. 首次部署公会时的基础迁移：20260730143000_guilds.sql、
   20260730143100_guild_idempotency.sql、20260730180000_guild_invite_and_detail.sql；
2. 已上线 sync-profile 后才能执行的权限迁移：20260731230000_profile_write_grants.sql；
3. 本次日建设：20260801010000_guild_commission_board.sql；
4. 本次功勋 / 据点 / 商店：20260801020000_guild_stronghold_economy.sql；
5. 最后执行一次 npm run edge:build，并部署 guild-expedition。

> 必须严格按“迁移 → Edge Function”执行。旧函数不会调用新 RPC，所以迁移期间已有
> 远征仍可玩；新函数上线后，功勋 / 委托 / 据点任一步失败都会让同一 request ID
> 重试，不能静默吞错造成“次数已扣但奖励漏发”。两边都部署完后，客户端刷新会自动
> 显示完整面板。

## 两账号验收

使用两个匿名账号加入同一公会：

1. 两人打开首页，确认可看见建设委托、赛季据点、当前功勋与三项收藏；旧后端应只显示“准备中”，不阻断团本。
2. 账号 A 完成团本并超过今日最好分：检查 guild_submission_requests、guild_merit_awards 与 guild_member_merits；同一 request ID 重试不得再次增加余额。
3. A 用功勋捐献 1 / 5 / 10 任一档：余额只扣一次、guild_merit_spends 与 guild_stronghold_sources 各只有一条对应 request ID。
4. A 和 B 将日建设推进到 1,800：声望只增加一次，guild_stronghold_sources 只记录当天一条 commission 来源。
5. 让全会周团本首次完成：据点只增加一次 raid 来源；刷新和较低分重试不得重复推进。
6. 以普通 authenticated token 调用 guild_award_merit 或 guild_apply_commission_stronghold 必须被拒绝；前者只能由 service_role 调用。
7. 刷新、断网或临时关闭函数时，本地挂机照常；公会页仅降级当前模块，不能阻断已有团本。

## 重新部署与回滚

- 只要 src/core、src/data 或 guild-expedition 相关代码变化，都必须重新运行 npm run edge:build 再部署函数。
- 临时回滚先回退前端或停止新函数调用；保留功勋、消费与据点来源账为只读审计数据，**不要删除表重置赛季**。
- 新赛季应提升 TRIAL_SEASON_ID，并在发布前确认据点阶段与收藏是否重置；不要复用旧赛季 ID。
