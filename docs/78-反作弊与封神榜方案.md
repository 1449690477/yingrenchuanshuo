# 78 · 反作弊与封神榜（外挂榜）方案

> 制订与施工：2026-07-31 小督。老板令：「做反作弊，A 方案（榜单公平优先）；
> 单开一个封神外挂榜，把作弊的人从所有榜单踢出去、单独列出来，让别人知道他改了什么、改了多少；
> **但必须准确，不能影响正常的高分玩家**。」

---

## 零、先说清楚一件事（这条决定了方案的形状）

**纯前端单机存档做不到「不准他们改任何东西」。** 游戏代码全在玩家浏览器里，
任何签名密钥、校验逻辑都随包发给玩家；他改完数值再调用我们自己的签名函数重算一遍摘要，
本地校验一律通过。这不是实现问题，是「裁判和选手是同一个人」的结构问题
（docs/71 §五.2、ADR-021 同一结论：客户端 HMAC/混淆只提高成本，不是防作弊）。

**所以本方案不承诺「改不了」，承诺的是：**

| 类别 | 目标 | 手段 |
|---|---|---|
| 会影响别人的（五榜/竞技场/公会） | **绝对改不了** | 服务端权威复算 + 物理上界 + 本方案的证据链与封神榜 |
| 纯自己单机的（挂机进度/金币/强化） | 改了**上不了榜、留下证据**，收益趋近于零 | 同上；不做客户端加固（B 方案，老板已选 A，暂不做） |

## 一、现有防线盘点（本次实测，全部已在线）

今天各线其实已经把地基建好了，本方案是**把它们串成证据链**，不是从零造：

| 路径 | 现状 | 结论 |
|---|---|---|
| 战力榜 | `sync-profile` 载荷**没有战力字段**，服务端按装备快照现算；另有 `combatPowerBound` 物理上界 | 改战力：**已不可能** |
| 试炼榜 | 服务端用同一份 core 复算伤害；装备逐件硬校验（定义存在/槽位/等级/词条数值上限） | 改分数：**已不可能** |
| 秘境榜 | 100ms 帧格律 + 两波物理上下界 + 深度链（报第 5 层必须先交 1~4 层） | 改用时：**已不可能** |
| 进度榜/里程碑 | 等级与关卡由服务端档案为准，表外一律拒 | 改进度：**已不可能** |
| 四张榜表 | 均有 `verified boolean default false`，不合理行只移出展示、不封号 | **封神榜的地基已经在了** |
| 存档本地 | PR#13 完整性信封（SHA-256 + revision + 主备链） | 能发现损坏与低成本编辑，挡不住重算摘要 |

**唯一的结构缺口**：以上拒绝**拒完就扔**，没有任何记录。
本方案补的就是这一环——**把拒绝证据留下来，封神榜的数据源与作弊遥测同时到手。**

## 二、封神榜设计

### 2.1 数据来源：证据表 `cheat_evidence`

每次服务端判定「这条提交在物理上不可能」时，写一行证据：

| 字段 | 含义 |
|---|---|
| user_id / display_name | 谁 |
| detected_at | 何时 |
| source | 哪条路径（submit-trial / sync-profile / submit-dungeon / …） |
| claim_field | 改的是什么（战力 / 试炼伤害 / 秘境用时 / 装备词条 / 等级） |
| claimed_value | 他报的值 |
| max_possible | 物理上限 |
| overage_ratio | **超了多少倍**（= claimed / max_possible） |
| bundle_version | 检测时的服务端核心版本（防版本漂移误判，见 §三） |
| published | 是否已上封神榜 |
| cleared_at / cleared_reason | 老板人工洗白（误判后的唯一撤回通道） |

### 2.2 展示：第六个页签「封神榜」

```
  封神榜 · 这些成绩物理上不可能存在
  ┌──────────────────────────────────────────────┐
  │ 小明   战力 999,999,999                       │
  │        物理上限 47,210 · 超 21,178 倍 · 07-31  │
  ├──────────────────────────────────────────────┤
  │ 小红   秘境用时 3ms                            │
  │        物理下限 8,400ms · 07-31                │
  └──────────────────────────────────────────────┘
```

**同时**：上榜者的全部正常榜单行 `verified=false`（移出展示），后续提交继续记录但不进榜。

### 2.3 ★ 准确性设计（老板最在意的一条，也是本方案最核心的部分）

公开点名一旦误伤，社会性后果不可撤回。所以判据只用**数学上不可能**，三道闸门齐开才公开：

**闸门 1 · 只认铁证，不认可疑**

| 采信（物理不可能，零误判空间） | **不采信**（统计可疑，会误伤肝帝/欧皇） |
|---|---|
| 战力 > 该等级该职业「每槽最强装+满掷+全+15」的结构上界 ×1.5 | 「进度比别人快」 |
| 秘境用时 < 两波怪的物理最短时间，或不是 100ms 整数倍（战斗按 0.1 秒一帧推进） | 「金币比别人多」 |
| 试炼伤害与服务端复算结果矛盾 | 「运气特别好」 |
| 装备词条值 > 该品阶该等级可能掷出的最大值 | 「氪佬装备特别好」 |
| 等级 > 120 或非整数 | 「深夜在线时间长」 |

判据全部复用**玩家实际结算那条链路**（`buildTrialCombatant` / `dungeonBoard` 格律），
不另立一套公式——docs/61 §2.2「同一口径两处实现，只有一处正确」的教训。

**闸门 2 · 倍率余量 ≥ 2×**

只超一点点的**一律不公开**（仅记录）。理由是真实存在的一个误判源：
Edge Function 的核心是打包快照，**若新装备已发给客户端而函数未重打包**，
合法的新装备玩家会小幅超过旧上界（docs/72 反复强调 `edge:build` 纪律正因如此）。
版本漂移造成的超额是 +10%~30% 量级，而真作弊的是「999999999」，两者差几个数量级。
**2 倍余量把版本漂移误判压到零，同时一个真作弊者都放不掉。**

**闸门 3 · 重复 或 极端**

- 2 次以上独立铁证 → 公开
- 或单次超 10 倍 → 公开（这种没有任何解释空间）
- 仅 1 次且 2~10 倍 → **只记录不公开**，进老板复核队列

**兜底**：`cleared_at` 人工洗白；证据带 `bundle_version`，若日后发现某版本上界本身有错，
可按版本批量作废该批证据。

### 2.4 不做的事（明确边界）

- **不封号、不清档、不扣数值**（docs/40 红线：不得没收玩家已得之物）——只移出榜单 + 公开陈列
- **不弹窗警告、不中断游戏**——本地玩得下去，只是上不了榜
- **不对正常玩家做任何新增校验**——本方案零新增客户端拦截，正常玩家路径一行代码都不变

## 三、准确性的形式化保证（给后人核对）

1. 所有上界函数都是**该等级该职业物理可达的最大值**，不是统计值；
2. 上界随内容自动扩展（`combatPowerBound` 运行时扫 `EQUIPMENT` 全表，新装备上线即自动纳入）；
3. 公开阈值 = 上界 × 2，因此需要「比物理最强还强一倍」才会被公开点名；
4. 证据不可变、带版本、可按版本批量作废、可人工洗白。

**结论**：一个正常玩家（哪怕全服第一的肝帝+欧皇+氪佬）被公开点名的概率为 0，
除非我们的上界函数写错了——而那需要错 2 倍以上，且有版本作废与人工洗白两道后悔药。

## 五、上线实测（2026-07-31 线上真实探针，非本地模拟）

对生产库与生产函数实打，五项全过：

| # | 项 | 结果 |
|---|---|---|
| ① | 匿名建会话 | OK |
| ② | **正常玩家提交（Lv5 空装）** | **OK，战力 298 —— 正常路径零影响** |
| ③ | 伪造快照（Lv5 穿 Lv76 传说武器） | **被拒**「装备等级超过角色等级」 |
| ④ | 封神榜匿名可读 | OK，条目为 **「装备等级 76，角色等级仅 5 · 超 15.2 倍」** |
| ⑤ | 证据表客户端直读 | RLS 拦截，返回空集（零行泄漏） |
| ⑥ | **恶意玩家伪造证据陷害他人** | **HTTP 400 被拒** —— 栽赃路径不存在 |

探针数据已全部清理，`cheat_evidence` 归零。

> ⑥ 这条是审计时才想到要验的：如果客户端能往证据表写行，
> 作弊者就能把正常玩家推上封神榜 —— 那比作弊本身更糟。已确认写不进去。
