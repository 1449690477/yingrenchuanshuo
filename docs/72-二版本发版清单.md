### 第 1 步结论（**已由我自己推翻，见下方更正**）

初版结论是「胜率随深度非单调、单靠 k(d) 标不出来」，并据此建议改深度步长。
**这个结论不成立，我在做验证实验时把自己否掉了。**

#### 更正一：我的模型不能当门禁用

我的玩家模型是「打第 d 层的人 = 该层标称等级」。两个致命问题：

1. **深层那几行描述的是不可能存在的人群。** 深度链要求先过 d−1 才能打 d，
   所以 d3 的人必然先在更低等级通过了 d1。我却给 d3 配了 Lv41 的玩家、
   给 d1 配 Lv31 的玩家 —— 那个 Lv41 的人若真存在，他打 d1 会是碾压，
   不会是我算出来的 3%。**行与行之间互相矛盾。**
2. **我的「典型装备」其实弱得不真实。** 实查：Lv31 取到的是 **Lv28 稀有**、
   Lv56 取到的是 **Lv50 史诗**，全部零强化 —— 落后 3~6 级且没养成。
   真实玩家不长这样。

所以「violet d1 只有 3%」这类读数是我的模型太弱造出来的，**不是墙**。
**@claude 的 4367df4 定稿没有被我的数据质疑。**

#### 更正二：我建议的解法 (A) 实测更糟，别采纳

我提议「把深度步长压在同一品质带内」（步长 3/5/5 → 2）。同一基线实测：

| | d1 | d2 | d3 | d4 | d5 |
|---|---|---|---|---|---|
| 现状（步长 3/5/5） | — | — | 0 | **100** | 100 |
| 改成步长 2 | — | — | 0 | **0** | 0 |

步长变小 → 玩家标称等级涨得更慢 → **永远够不到品质跳档**，
于是墙之后不再回弹，而是一路不可能。**(A) 把「中间有墙」换成了「墙永久」。**

#### 唯一还站得住的一条，降级为发版后观察项

「玩家战力随等级是阶梯（品质跳档）、怪物随等级平滑」这个机制本身成立。
它在 @claude 的固定入场模型下不会显形（那个模型里玩家不跨品质线），
但**如果真实玩家是边升级边往下爬**，他会在跨品质线的前一层感到明显难、
跨过之后突然变简单。这是**节奏观察项**，不是标定 bug，
建议上线后看真实数据，不阻塞发版。

## 四、发版当天的收尾清单

按顺序做，每条都要有**实测**而不是「应该没问题」：

1. `npm run verify` + `npm run build` + `npm run edge:build` 全绿（隔离 worktree 上跑，**不要在共享工作树跑 edge:build**）
2. 受内容影响的 Edge Function 重新部署（改过 `src/core` 或 `src/data` 就必须重打包，docs/62 教训）
3. 推 main → 等 Pages run 成功 → **抓线上 bundle 确认新代码真的在里面**（不是看工作流绿就算）
4. 线上探针：每个榜至少读一次真实行数；新函数至少验一次拒绝路径 + 一次写入路径
5. 更新 `docs/31-PROGRESS.md` 的状态表与变更日志
6. 频道 `release` 掉自己的 claim
7. **PWA 是 prompt 更新**：玩家必须点「发现新版本」才会加载新包，发版通知里要写这句
