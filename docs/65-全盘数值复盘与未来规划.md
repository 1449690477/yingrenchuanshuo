## 一、方法：先建基准，再逐个系统对照

docs/56 之后，「玩家在 Lv N 该有多强」有了单一权威口径
（`expectedBuildCp`）。复盘就是把每个系统的硬编码等级锚点拿来和它对照。

实测基准（每 5 级）：

```
Lv 1=  284(common)  Lv16= 2483(fine)   Lv26= 6456(rare)   Lv41=17649(epic)
Lv56=26595(epic)    Lv61=29773(epic)   Lv66=52983(legendary)
```

**这条曲线是阶梯形的**，单级增幅 >12% 的断崖只出现在品质跃迁点：

| 断崖 | 单级增幅 |
|---|---:|
| Lv15（common→fine） | +46% |
| Lv25（fine→rare） | +52% |
| Lv40（rare→epic） | +58% |
| Lv65（epic→legendary） | +64% |

阶梯本身是健康的 —— 拿到第一件传说**就该**有飞跃感。
问题出在**台阶之间的平台有多长**（见 §三）。

## 二、已修：试炼分段（`f3bb0a9`）

旧分段是「等级无上限、内容到 Lv120」时代的配置：

| 旧分段 | 段内战力跨度 | 实际玩家 |
|---|---:|---:|
| 初樱 1-30 | **27.3×** | 13 / 20 |
| 绯月 31-60 | 3.6× | 5 |
| 琥珀 61-90 | 4.3×（实际只到 68） | 2 |
| 绯樱 91-120 | —— | **0，永久不可达** |

分段存在的唯一理由是「同水平比较」（docs/51 §3.4）。
27.3× 跨度里 Lv30 对 Lv2 是碾压，而 65% 的玩家都挤在这一段。

### 2.1 重划的关键判断：按停留时间加权，不按等级平均

这是本次复盘最重要的方法论产出。**等级不是均匀消耗的资源**：

| 区间 | 停留时间 |
|---|---:|
| Lv1~23 | 约 1.5 天（sim：D1 就到 Lv21） |
| Lv24~39 | 约 5 天 |
| **Lv40~68** | **约 22 天** |

所以低段跨度大**无所谓**（明天就换段了），而 Lv40~68 必须切细 ——
竞争真正发生在那里。等战力跨度四等分会得到均衡的数字，
但把 22 天的主战场留在同一段里，是优化错了目标。

重划后跨度：**3.9× / 3.1× / 2.7× / 1.5× / 2.1×**，最大跨度落在只待半天的过渡段。

### 2.2 段数为什么取 5 而不是更多

分段越多越公平，但**人少时段数过多会把榜切空**。
同一天刚踩过这个坑：8 条试炼成绩被 3 分段 × 4 职业切成 12 个桶，
邻域榜大多是空的或只有自己（docs/61 §3.2）。
公平与密度的取舍，在玩家规模上来之前必须偏向密度。

### 2.3 id 全换新 + 保留旧 id 供存档校验

旧 id 语义变了（`hupo` 从 61-90 变成 24-39），继续复用会让上周 Lv65 玩家的
成绩显示在低段榜上 —— **比看不见更糟**。
旧 id 保留在 `LEGACY_TRIAL_BRACKET_IDS`，只用于存档校验：
老档的历史 `TrialBest` 必须还能读出来（铁律 5）。

## 三、待做：r5 是成长凹陷

### 3.1 实测

| 区域 | 等级 | 战力增幅 | 品质变化 |
|---|---|---:|---|
| r1 | 1-10 | 3.91× | 全程 common |
| r2 | 10-20 | 2.91× | → fine |
| r3 | 20-30 | 2.39× | → rare |
| r4 | 30-40 | 2.21× | → epic |
| **r5** | **40-52** | **1.41×** | **全程 epic** |
| r6 | 52-65 | 2.15× | → legendary |

### 3.2 先排除了「模型盲区」这个解释

`expectedBuildCp` 不含套装效果，所以我先验证 r5 的绯焰套能不能补上差距：

```
Lv40  无套装 17088  绯焰6件 17554  → +2.7%
Lv52  无套装 24119  绯焰6件 24773  → +2.7%
```

只有 **+2.7%**，因为 6 件效果是「15% 概率追加炎爆伤害」这样的**概率触发**，
不进战力面板。算上满套 r5 也只有 1.45×。**凹陷是真的。**

### 3.3 根因：epic 品质带独占 25 级 ≈ 20 天

| 品质带 | 等级 | 跨度 |
|---|---|---:|
| common | 1-14 | 14 级 |
| fine | 15-24 | 10 级 |
| rare | 25-39 | 15 级 |
| **epic** | **40-64** | **25 级** |
| legendary | 65-68 | 4 级（内容顶） |

换算时间：前 8 天拿到 4 次品质升级，然后 **20 天只有最后那一次**。
r5 整段落在这个平台里。

### 3.4 还有一层：r5 的成长藏在看不见的地方

`AVG_SKILL_MULTIPLIERS` 在 Lv45 从 1.7 跳到 2.0（+18%），正好在 r5 内。
但技能倍率影响 DPS 不进战力面板 —— **玩家看到的数字是平的，实际输出在长**。

从胜任感（docs/40 / SDT）角度看，**看不见的成长不解渴**。
这解释了为什么 r5 段的体感比数据更差。

### 3.5 三个候选方案（未定，等 codex 释放文件后决策）

| 方案 | 做法 | 风险 |
|---|---|---|
| **A 切分 epic 带** | 把 epic→legendary 边界从 Lv65 下移到 ~Lv52 | 会把 r6 变成新的凹陷（r6 全程 legendary），只是把问题搬家 |
| **B 让 r5 的成长可见** | 把绯焰 6 件的概率触发改成/追加面板属性；或让 Lv45 的技能倍率跃迁在 UI 上明示 | 概率触发比纯数值有趣，改掉可惜；「明示」是 UI 活不是数值活 |
| **C 给 r5 一条独立成长轴** | r5 是套装工坊所在（绯焰套合成），把「集齐套装」做成 r5 的显式主线目标而不是副产物 | 需要内容设计配合，不只是调数 |

**我的倾向是 B + C 组合、不动品质带**：品质带是 `expectedBuildCp` 的输入，
而后者是推荐战力、章节门槛、竞技场装备品质的共同来源，动它要重跑全部门禁，
收益（消除一个平台）不值这个风险。而 B 只改一个套装的效果构成，
C 是内容侧的目标呈现，两者都局部可控。

> **不采纳「新增一档品质」**：品质阶梯（common→divine 共 8 档）
> 是全局系数表，插一档要改所有区域的品质组、装备生成、洗练容量、
> 竞技场跟随公式。为了一个平台期动地基，代价过高。

## 四、待决策：体力系统已经不起作用了

### 4.1 实测

```
上限 120，恢复 5 分钟 1 点 → 每天恢复 288 点
挑战未通关关卡消耗 6 点/次
玩家每天推进 2~3 关 → 每天消耗 12~18 点
```

**供给是需求的 16~20 倍。** 体力永远不会成为约束。

### 4.2 为什么会这样：它的职责被别人接走了

体力在 docs/56 里的设计目的是「阻止玩家快速重复挑战冲穿内容」。
但同一次重构引入的 `clearCycles`（通关所需循环数，r6 已到 340）
把节奏刹车做得彻底得多 —— **一关要磨几小时**，重复挑战根本不是瓶颈。

于是体力从「刹车」退化成「装饰」。它甚至可能有害：
玩家看到一根永远满的条，会以为那是需要经营的资源。

### 4.3 三个选项

| 选项 | 说明 |
|---|---|
| **A 删掉** | 最诚实。但要动存档字段、UI、日常恢复逻辑，改动面不小 |
| **B 改成有意义的闸** | 给「扫荡」「副本次数」等真正需要限次的地方用，主线推进不再消耗 |
| **C 保留但从 UI 隐藏** | 代码不动，只是不再向玩家展示一个不起作用的数字 |

**原倾向 B，但 2026-07-31 查证后发现它暂时没有落点**：
`SWEEP_STAMINA_COST` 虽然定义了，但**扫荡系统根本没有实装** ——
全仓除了常量声明之外没有任何引用。装备副本也有自己独立的每日次数
（`dailyClears: 3`），不走体力。所以「把体力挪到扫荡与副本次数」
现在无处可挪。

**结论：这件事需要排期，不适合顺手做。** 三个选项各有前置：
A 删掉要动存档结构，而 @claude-drops 正在做 SAVE_VERSION 15 → 16
（深度进度字段），**两个并发的存档迁移会撞**；
B 要先实装扫荡；C 要动 UI，而 UI 侧现在有人在改。

在此之前它是无害的（一根永远满的条），只是**看起来像资源而实际不是**。
下一个空档期做，做的时候三选一要连带把 `SWEEP_STAMINA_COST` 一起处置 ——
它现在也是没有落点的孤儿常量。

## 五、我的一次误判（记下来，避免重犯）

复盘中我一度判定「珍品定价过高、玩家买不起」，依据是：

```
红装解锁时累计金币 8,195,701，最便宜一件 11,000,000 → 0.75×
```

**这个结论是错的**，因为我只看了「解锁那一刻」这一个时点。
把有效窗口算全之后：

| 系列 | 攒够钱 | 被同期掉落追上 | 有效窗口 |
|---|---|---|---|
| berry-cream 紫 | 第 35 关 | 第 69 关 | 34 关 |
| moon-sugar 黄 | 第 47 关 | 第 95 关 | 48 关 |
| **rose-night 红** | 第 64 关 | 第 123 关 | **59 关** |
| cardboard-cat | 第 43 关 | 第 75 关 | 32 关 |

红装解锁在第 60 关、第 64 关就买得起（r2 节奏下不到一天），
然后能用 59 关才被掉落追上。**定价是健康的。**

> **教训**：判断「买得起吗」不能只看一个时点，要看
> 「攒够钱的时刻」与「变得无用的时刻」之间的窗口。
> 单点比值会把「需要攒几天」误判成「永远买不起」。

## 六、~~Lv120 时代的死配置清单~~ → 这一节我写错了，区域 7 当场证伪

> **2026-07-31 勘误。原文把几处「当前不可达」的配置列为死配置建议清理，
> 这个判据是错的。**

原文列了三处「按 Lv120 配置、现在永久不可达」的条目，其中两处建议清理：
`STAMINA_CAPS` 的 minLevel 70 / 100 档、`AVG_SKILL_MULTIPLIERS` 的 minLevel 85 档。

**区域 7 上线当天就证伪了这条建议**：内容顶从 65 涨到 78，软上限随之从 68 变成 **81**，
`STAMINA_CAPS` 的 **minLevel 70 那档立刻变成活的**，真的在给玩家把体力上限抬到 180。

如果当初照原建议删掉，区域 7 会**静默丢掉这个档位** —— 没有报错、没有测试会红，
只是玩家的体力上限少了 60 点，而且没人知道为什么。

### 6.1 正确的判据

**「当前不可达」不等于「死配置」。** 判据不是今天能否达到，
而是**设计上是否打算让它随内容自动生效**。

讽刺的是我在同一份文档 §7.1 第 2 条就写过正确的原则
（「能跟随内容的用公式」），也在 docs/60 §2.3 明确说过
`typicalQualityAt` 的 mythic / divine 两档「是给未来留的，不要删」——
却对体力与技能倍率的档位用了相反的判据。**同一个人在同一天用了两套标准。**

### 6.2 现状（区域 7 后，软上限 81）

| 位置 | 条目 | 状态 |
|---|---|---|
| `STAMINA_CAPS` | minLevel 40 → 150 | ✅ 可达 |
| `STAMINA_CAPS` | **minLevel 70 → 180** | ✅ **区域 7 后已生效** |
| `STAMINA_CAPS` | minLevel 100 → 240 | ⏳ 等区域 8/9 |
| `AVG_SKILL_MULTIPLIERS` | minLevel 65 → ×2.3 | ✅ 可达 |
| `AVG_SKILL_MULTIPLIERS` | minLevel 85 → ×2.6 | ⏳ 等区域 8/9 |
| `typicalQualityAt` | mythic(90+) / divine(110+) | ⏳ 等区域 8/9 |

**一条都不要删。**

### 6.3 已加的守卫（`core/__tests__/progression.spec.ts`）

与其靠文档提醒，不如让代码拦住。新增 5 条结构守卫：

| 守卫 | 防的是什么 |
|---|---|
| 必须按 minLevel **降序** | 查找用 `.find(level >= minLevel)` 取首个匹配，**升序会静默取错档** —— Lv80 玩家会拿到 minLevel 1 那档 |
| 必须有 minLevel 1 兜底档 | 查找末尾有非空断言，缺了直接崩 |
| 取值随等级单调递增 | 高等级档不能比低等级档差 |
| 超限档保留 | 把「它们是有意留的」写进测试，让下一个想清理的人先读到理由 |
| 软上限内每级都能取到值 | 内容涨了而阶梯没跟上时会红 |

第一条尤其值得强调：降序是**查找正确性的前提**，而按 minLevel 升序排列
是绝大多数人的直觉。改错了不会报错、不会有人发现，只是数值悄悄不对——
这类回归比崩溃危险得多。

## 六之二、战力榜当前可被玩家自填（2026-07-31 发现）

> 由 `@kimi-boards` 在设计进度榜时发现，我实测确认。**不是数值问题，是权限口径问题**，
> 但因为它决定「榜单能不能信」，记在这份数值文档里。

`profiles` 的写策略是：

```sql
create policy "own profile upsert" on public.profiles
  for all using (auth.uid() = id) with check (auth.uid() = id);
```

`for all` 意味着**已登录玩家可以任意 PATCH 自己那一行的任何列** ——
包括 `combat_power`。也就是说**战力榜的名次现在是客户端自填的**。

实测：匿名 key 的写入被 RLS 挡住（非破坏性 PATCH 返回空数组，零行受影响），
但那只是因为 `auth.uid()` 为 null；任何真实玩家的 JWT 都能改自己那行。

### 危害评估

docs/51 §4 刻意把战力榜放在**次级页签**（「玩家期待看到、但不是我们希望他追的」），
所以危害小于试炼榜。但**一个假的第一名照样会打击真实玩家** ——
榜单的价值建立在「上面的数字是真的」之上，一旦不可信，整块 UI 就是负资产。

### 两个处置方向（未定，待排期）

| 方向 | 做法 | 代价 |
|---|---|---|
| **A 收权限** | `combat_power` 改为只有 service-role 能写，客户端经 Edge Function 上报 | 要新增一个函数，且档案同步链路要改 |
| **B 加合理性下界** | 榜单侧过滤 `combat_power ≤ expectedBuildCp(level) × 上限系数` | 不改权限，复用**同一个单一权威口径**（§7.1 第 1 条），成本低；但改不了「数据本身是脏的」 |

**倾向 A + B 都做**：A 堵住源头，B 作为纵深防御 ——
即便将来某个新写入点又把权限放开，B 仍然会把离谱值挡在榜外。
这与试炼榜「服务端复算」+ 里程碑「硬下界」是同一套分层思路。

### 顺带的通用结论

**新榜单一律不要挂在 `profiles` 上。** 竞技性榜单必须用专用表、
RLS 只读、只有 service-role 能写（`milestones` / `dungeon_records` / `progress_records` 都是这个形态）。
`profiles` 只适合放**展示性**字段（名字、头像、简介），
因为它的写策略天然是「玩家自治」的。

## 六之三、威胁轴全程漂移 4.7×：后期怪物结构性打不死玩家（2026-07-31 发现）

### 6.3.1 现象

用真实关卡数据实测「**安全边际** = 玩家能扛几击 ÷ 杀死怪要几击」：

| 等级段 | 普通关安全边际 |
|---|---|
| Lv10~19 | 2.63 |
| Lv30~39 | 3.80 |
| Lv50~59 | 6.12 |
| Lv70~79 | **12.21** |

**4.7 倍单调漂移。** Lv10 时怪物打你 2.6 轮就能致命，Lv70 时要 12 轮。
裸公式外推到 Lv120 是 **63×**（能扛 745 击、只需 12 击就能杀死对方）。

### 6.3.2 根因：品质阶梯只抬玩家，不抬怪物

台阶落在 **65 / 90 / 110**，正是 `typicalQualityAt` 的品质跃迁点。
品质阶梯是 common 1.0 → divine 15.0 的**乘法**阶梯，每跨一档
玩家的有效血量成倍跳；而 `monsterAtk(level)` 只随等级平滑增长，
**没有任何东西跟着抬**。

### 6.3.3 为什么一直没人发现：全仓只有节奏轴的量具

`scripts/simulate.ts` 原有的【增速对比】量的是
「玩家战力 vs **怪物血量**」—— 那是**节奏轴**（打多久），它一直是绿的。
战斗的另一条轴是**威胁轴**（会不会死），而在此之前**全仓没有任何量具在看它**。

这与装备副本深度那次是同一个结构性教训，两处独立撞上：
**血量管节奏、攻击管生死，两条轴必须分别有量具**，
否则其中一条可以漂到几十倍而所有门禁全绿。

### 6.3.4 已做：量具上线，只报不拦

`reportThreatAxis()` 已加进 `npm run sim`，每次都会打印上表并在
漂移 > 3× 时输出警告。**没有做成硬门禁**，因为现在翻红只会让所有人
习惯性忽略它 —— 修它要动品质阶梯或怪物攻击曲线，属于标尺结构改动。

> **写量具时我自己踩的坑，记下来**：第一版我拿「最危险一关」那列算漂移，
> 读出来 2.0× 并**报了绿灯** —— 那列是全段最极端的单只怪，被个别高倍率
> BOSS 主导，噪声大到能把 4.7× 的真实漂移吃掉。
> **量具选错列比没有量具更坏，因为它会主动给出绿灯。**

### 6.3.5 待做：与 CP 暴击定价同批修

这条和 `combatPower` 对暴击的错价（频道 2026-07-31「实锤 B」）是
**两个独立的失真源、方向不同**：

| 失真源 | 失真维度 | 表现 |
|---|---|---|
| 实锤 B：CP 对暴击定价错 | **职业间** | 高暴击职业（喵喵暴击 10 = 剑姬 2 倍）真实强度被系统性低估 |
| 本节：威胁轴漂移 | **等级段间** | 同一个战力比，低等级段会死、高等级段全胜 |

## 七、未来的数值规划方向

### 7.1 已经确立、应当继续遵守的四条

1. **单一权威口径**。「该有多强」只有 `expectedBuildCp` 一个来源，
   推荐战力、章节门槛、竞技场装备品质全部从它派生。
   任何新系统要判断强弱，去读它，不要另立标准。

2. **能跟随内容的用公式，需要可比性的用常量**。
   这两者是**相反**的，必须分清：
   - 竞技场装备：**公式**（`typicalQualityAt(MAX_CONTENT_LEVEL)`），
     内容涨它自动涨，永远等于同期主线最强
   - 里程碑档位：**常量**（20/40/60 固定），
     一旦移动，已写下的记录就失去可比性
   判断标准：**这个数字会被写进历史记录吗？** 会 → 常量；不会 → 公式。

3. **门禁是唯一裁判，不写天数目标**。
   docs/59 我曾同时写「系数 400~500」和「r7 耗 10~12 天」，
   两者不可能同时成立（10~12 天正是 r6 的跨度）。
   天数是系数、内容量、玩家成长三者的合成结果，拍脑袋估必错。
   新区域只写「系数单调递增 + sim 门禁全绿」。

4. **按停留时间加权，不按等级平均**（本次新增）。
   等级不是均匀消耗的：Lv1~23 只待 1.5 天，Lv40~68 要待 22 天。
   任何按等级分段的系统（分段、品质带、门槛）都该问一句
   「玩家在这一段待多久」，而不是「这一段有多少级」。

### 7.2 下一个区域（r8）上线时要做的数值动作

按顺序，每一步都有明确的裁判：

1. `STAGE_PACING_FACTORS[8]` 必须 **> r7 的 440**（单调性硬约束）
2. 追加里程碑档位（r7 后 Lv80，r8 后可能 Lv95）—— **只追加，不移动旧档**
3. 复核试炼顶段是否需要再拆（`b_crown` 现在开口到 120，
   内容涨到 Lv78 后它的跨度会变大，届时按 §2.1 的停留时间原则重算）
4. `npm run edge:build` + 重新部署 —— **区域数据在 Edge Function 的打包链上**
5. 全量 sim + 各区经济门禁 + 装备副本平衡门禁

### 7.3 长期观察项（还不到动手的时候）

- **品质带宽度**：epic 25 级是目前最长的平台。内容涨到 r9（divine 段）后
  再看整体分布，若仍有 20 天级的平台，那时才值得考虑动品质带
- **战力面板的覆盖面**：技能倍率、套装概率触发都不进战力，
  导致「实际变强但面板不动」。若玩家反馈集中在「感觉没变强」，
  该做的是让面板更全面，而不是加数值
- **反作弊下界的理论化**：里程碑用时下界现在是「sim 典型 × 0.2」的经验值。
  更硬的做法是从「升到 Lv N 所需总经验 ÷ 最优刷图的最大经验速率」
  推物理下界。等出现可疑成绩再做

## 八、给其他 AI 的交接要点

- **数值改动前先读 `expectedBuildCp`**，不要自己另算一套「该有多强」
- **改了被 Edge Function 打包的任何 `src/core` 或 `src/data` 文件**，
  必须 `npm run edge:build` 并重新部署，否则客户端与服务端跑两套规则
  （今天踩了三次：邻域榜 SQL 口径、竞技场装备只改客户端、分段表）
- **共享工作树里跑 `edge:build` 会把别人未提交的改动一起打包**
  （esbuild 读磁盘不读 git）。跑之前先 `git status`
- **测试断言性质，不要断言具体数值/id**。把分段区间写死等于把测试变成
  「设计快照」，每次调数都要改一堆断言，还会掩盖真正的回归
- **给函数加严格守卫时，检查所有调用点**，尤其「预览/展示」这类
  不产生真实对象的路径（今天商店就是这么炸的）
