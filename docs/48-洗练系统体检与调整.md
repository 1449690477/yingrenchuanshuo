# 48 · 洗练系统体检与调整

> 所有者反馈：「这个洗练的推荐系统逻辑和整体逻辑还有 UI 有点问题」，
> 并把后续完善交给数值/逻辑侧决定。
>
> 本文档记录本轮查到的四个问题、各自的根因与处理，以及尚未动的部分，
> 供 codex / kimi 后续接手。数值由 claude 负责。

## 一、推荐排序无视「这件装备还穿不穿」

### 现象

工坊四个推荐位清一色「史诗 · 背包 · Lv20」，而玩家身上穿的是更高级的装备。
玩家照着推荐洗，洗的全是永远不会上身的东西。

### 根因

`priority` 由规则档位常量主导：

| 规则 | 基础分 |
|---|---:|
| 死词条 | 108 |
| 他职专属 | 96 |
| 同调 | 78 |
| 铭刻 | 68 |
| 淬炼 | 52 |
| 重铸 | 42 |

而装备本身只以 `worthScore × 0.2~0.3` 参与，其中等级又只按 `level / 10` 计入。
**Lv20 与 Lv80 的差距不到两分**，乘 0.3 之后连一分都不到。
于是「哪条规则更紧急」彻底压过「这件装备还穿不穿」。

### 处理

新增相关度模型（`src/core/reforgeAdvisor.ts`）：

- `referenceLevelOf`：以穿戴中的最高等级作为「玩家在用的装备等级」
- `relevanceOf`：
  - 穿戴中 → `1`
  - 同部位正穿着的那件不比它差 → `0`（永远不会换上去）
  - 等级不到在用装备的 **70%** → `0`
  - 其余 → `min(1, 0.45 + 等级比 × 0.35)`
- 排序分 `sortScoreOf` = `priority × relevance + (穿戴中 ? 40 : 0)`
- `relevance === 0` 的不再产出任何建议，但仍可手动选中洗练

效果：「身上这件需要同调」`78×1+40=118` 排在
「背包同级备选有死词条」`108×0.6≈65` 前面 —— **先修正在生效的装备**。

> 70% 这个门槛的取法：装备主属性按 `L^ITEM_POW` 增长，
> 落后三成等级大致等于落后一个品质档，此时无论词条洗得多好都不会换上去。

## 二、操作台与建议不同步（会让玩家白扣材料）

### 现象

卡片上写着「建议同调」、推荐横幅也写着同调，**操作页签却停在默认的「重铸」**。
玩家顺手点「洗练一次」就会做错操作，材料照扣。

### 根因

`ReforgeStudio.vue` 开局只设了 `selectedUid`，没设 `operation`，
后者始终是 `ref('reforge')` 的初值。切换装备卡片时同理。

### 处理

抽出 `adoptRecommendation()`，在两处调用：开局初始化、点选装备卡片。
同步操作与同调目标。操作页签仍在旁边，玩家想改随时能改。

## 三、共鸣值（保底）几乎摸不到

### 现象

界面常年显示「共鸣值 0 / 20」，且经常卡在某个数字不动。

### 根因

原增长表 `T1:+2 / T2:+1 / T3:0`，T4/T5 清零。
`AFFIX_TIERS` 权重 40/27/18/11/4，即 **P(T4或T5) = 15%**。

非好词条平均只推进 `1.26` 点，要**连续 16 次不出 T4/T5** 才能填满 20，
概率约 `0.85^16 ≈ 7.5%`。实测保底只贡献 **7.8%** 的 T4+ 产出 ——
玩家盯着的那条进度条基本永远填不满，还经常因为 T3 不加分而卡住。

### 处理

改为 `T1:+3 / T2:+2 / T3:+1`，**上限仍是 20**（不触动存档校验与既有迁移）。

| 增长表 | 保底占比 | 平均次数/T4+ |
|---|---:|---:|
| 原 +2/+1/0 | 7.7% | 6.23 |
| **现 +3/+2/+1** | **22.8%** | **5.37** |
| +4/+2/+1 | 29.0% | 5.02 |

选 22.8%：倒霉的人有兜底，运气好的人本来也用不上它。
且 T3 也推进进度条，**每一次不如意都看得见前进**。

> 之所以不动 `REFORGE_RESONANCE_MAX`：老存档里的 `reforgeResonance`
> 可能大于新上限，会撞 `assertResonance`，要额外写迁移。改增长表零风险。

## 四、随机洗练会误伤好词条，界面却不提示

### 现象

重铸/淬炼/铭刻都是「从**未定契**的词条里随机挑一条改掉」。
一件三词条的装备只要有一条 T4，不定契就有 **1/3** 概率把它洗没。
界面原本只说「本次会从全部 3 条中随机选 1 条」，没人会自己去算这个概率。

### 处理

- `ReforgeRecommendation.protectIndices`：随机操作时标出该保护的词条
  （门槛 **T4**，见下）
- 界面新增橙色提示条：「本次有 **33%** 概率洗掉「暴击率」」+「定契保护」按钮
- 该按钮只设定 `lockedIndices`、刷新费用预览，**不直接花材料**；
  材料仍在玩家点「洗练一次」时才扣

> 门槛定在 T4 而不是 T3：T3 还在随机洗练的期望附近，
> 锁它等于花材料保护一条本来就容易再摇出来的词条。

## 五、小屏适配

`320×568` 实测：装饰性头部 `min-height: 128px` 吃掉 **23%** 的屏幕，
正文只剩 440px —— 推荐横幅加装备轨就占满了，洗练台要滚很久才看得到。

| 断点 | 处理 | 头部高度 | 占屏 |
|---|---|---:|---:|
| 默认 | — | 128px | 23% |
| `max-height: 700px` | 压缩内边距、缩标题、隐藏装饰星点 | 84px | 15% |
| `max-height: 560px` | 再隐藏主标题，只留身份与件数 | 62px | 13% |

四个操作卡在 320px 上各 63px 宽、齐平 84px 高、无溢出；全程无横向滚动。

另修 `.advisor-banner` 被压扁的问题：它带 `overflow: hidden`，
而 **flex item 的 `min-height: auto` 在 `overflow` 非 `visible` 时会解析成 0**，
于是能被压到远低于内容高度再自行裁掉（实测内容 197px 只渲染出 74px）。
修法是 `.studio-body > * { flex-shrink: 0 }`。

> 这条对 kimi 后续做浮层通用：**滚动 flex 列里任何带 `overflow: hidden`
> 的子块都要显式 `flex-shrink: 0`**，否则会被压扁并裁掉内容。

## 六、查证后确认「不是问题」的

- **死词条会不会一直被洗出来**：不会。`skillMul` 的 `generation` 也是
  `deferred`，新掉落与重铸候选都不会产出它，只在老存档的旧装备上残留。
  推荐引擎的「先换掉死词条」正是这批遗留装备的清理路径。

## 七、尚未处理，留给后续

1. **低档副本装备的去处**（承 [`47`](47-装备副本门槛与奖励重排.md) 第 4.2 节）：
   洗练材料可以考虑接受淘汰装备分解，让「已淘汰 77 件」有出口。
   目前这 77 件除了占背包没有任何用途。
2. **定契费用曲线** `2^(N-1)`：锁 3 条要 4 张、锁 4 条要 8 张。
   八词条装备（心虹珍藏扩到 8 槽）上锁 6 条要 32 张，可能过陡，
   等玩家实际摸到八槽装备后再看数据。
3. **推荐引擎目前不看装备的强化等级差**：`worthScore` 里 `enhance × 2`
   参与很轻。若之后强化投入变重，应把它并入相关度。
4. **构建产物用了媒体查询 Level 4 范围语法**（全项目性问题，非本次引入）：
   打包后 `@media (max-height: 700px)` 会被压缩成 `@media (height<=700px)`。
   该语法需要 Chrome 104 / Safari 16.4 / Firefox 102，**高于 Vite
   默认 target 所暗示的下限**；老浏览器会整块跳过。
   产物里已有 13 处 `width<=`、3 处 `width>=` 是同样情况，
   本次只是又多了 2 处 `height<=`。
   小屏往往正是老设备，若要照顾它们，应由构建配置负责人显式设置
   `build.cssTarget`，而不是各组件绕开写法。
