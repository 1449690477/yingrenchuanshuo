## 零、这一轮改了 docs/63 的一个口径

docs/63 §二写的反作弊是「用时下界由 `npm run balance:equipment-dungeon`
的 TTK 推导」。**这条不能照做，它会把大批合法成绩判成作弊。**

秘境只有解锁等级下限、**没有等级上限**：一个 Lv65 的玩家随时可以回头去打
16 级的晴蓝档，两波各一帧秒杀。而 sim 的 TTK 是在「战力比 ≈ 1」的
对位强度下测的（晴蓝 18.4s、月紫 27.2s、琥珀 37.1s）——
按它 × 余量设下界（比如晴蓝 3.7s），等于宣布
「满级玩家不许回头刷低档副本」。

所以本轮的下界改成**结构性**的，与玩家强度无关：

| 层 | 判据 | 为什么它是结构性的 |
|---|---|---|
| L1 | 该层必须存在，且档位未挂 `comingSoon` | 封着的档位谁都进不去，此刻报成绩必然是伪造 |
| L2 | 用时是 100ms 的整数倍，且 ∈ [200ms, 180000ms] | 战斗按 0.1 秒一帧推进（`TICK_MS`），用时 = 帧数 × 100；两波各至少一帧 = 200ms；单波超 90 秒判负，所以胜利记录不可能超两波上限 |
| L3 | **深度链**：报第 d 层，服务端自己的表里必须已有同档第 d−1 层的可信记录 | 见下方 §0.1 —— 这条 2026-07-31 随 docs/66 换过一次，是本轮最重要的改动 |
| L4 | 首通时刻 ∈ [2026-01-01, 服务端时间 + 5 分钟] | 它是**并列时的排序依据**，所以「把时刻改成 1970」是一条真实的作弊路径 |

### 0.1 L3 为什么从「等级门槛」换成「深度链」

初版 L3 查的是 `profiles.level >= stage.unlockLevel`。docs/66 的深度模型
**删掉了 `unlockLevel`** —— 那条判定会退化成恒真：
一个失效了、却不会让任何测试变红的安全判定，比直接报错危险得多。
（这个风险由 @claude-drops 在改造预警里点名，本轮据此重做。）

新判据是深度链，关键在于**它查服务端自己的成绩表**：

```
要提交第 d 层  →  select max(depth) from dungeon_records
                  where user_id = 我 and tier_id = 该档 and verified
              →  要求 d ≤ 已达最高层 + 1
```

为什么不查客户端上报的存档 `depth` 字段：那是**被判断的人自己的声明**。
换成服务端账本之后，想伪造第 5 层的成绩，必须先把 1~4 层一层层交上来，
而每一层都要各自过一遍格律与上下界 —— 证据是服务端一层层收下来的。

第 1 层永远放行（链的起点）。换设备的玩家把本地阶梯**按深度升序补交**即可，
链会一层层重新建起来；这一条要写进 UI 的上报顺序，见 §四。

**榜单的「一座」也随之改变**：从关卡变成关卡的某一层，
id 直接用存档记录键 `${stageId}_d${depth}`（由 core 的
`equipmentDungeonRecordKey` 生成，不在别处拼字符串）。
理由是不同深度是难度完全不同的战斗，用时排在一起没有意义。

L1 / L3 不通过 → 400 拒收（结构性矛盾）。
L2 / L4 不通过 → `verified = false`：移出展示、保留数据、不封号
（docs/51 §6 既有处置口径）。

**副作用是好的：这个榜不再需要等区域 7。**
白名单从 `EQUIPMENT_DUNGEON_TIERS` 的 `comingSoon` 推导，codex 解封绯樱档
那天，服务端与客户端同时自动放开，**没有任何一行代码需要改**。
（docs/63 原本把「等 codex 解封后才能定下界」列为前置，那是统计型下界
才有的依赖。）

> **这条在写完一小时内就被验证了一次。** codex 的区域 7（3b361c0）落地、
> 绯樱档 `comingSoon` 去掉之后，白名单从 24 座自动变成 32 座，
> `edge:build` 自检直接打印「32 座已解封副本」——
> 服务端、Edge Function、迁移、网络层**一行都没改**。
> 唯一需要人动手的是两条写死座数的测试断言与本文档，
> 它们红了正是设计好的提醒信号；断言已改成「白名单恰好等于未封存的副本」
> 这种不随内容失效的形式。

### 二之一、线上端到端探针查出来的两件事（2026-07-31）

**① 上报前必须先有档案。** `dungeon_records.user_id` 外键指向 `profiles`，
没档案的账号连第 1 层都插不进去。改造前它只会回一句
「写入失败，请稍后重试」—— 一句既没解释原因、重试一万次也不会好的话。
现在显式检查并回「请先同步榜单档案再上报秘境成绩」。
**UI 侧的含义**：上报前确保 `sync-profile` 已经跑过（客户端打开榜单时
本来就会调它），否则玩家会撞上一条他无法自行解决的错误。

**② `improved: false` 有两种完全不同的含义，必须分开。**
探针实测：报一个破格律的用时（1337ms），返回 `improved: false` 且
`verified: true` —— 因为库里那行是老的可信记录、没被改写。
只看这两个字段，玩家无从知道**自己刚交的那条被判了不可信**。
所以加了 `claimVerified`：

| 情形 | improved | verified | claimVerified |
|---|---|---|---|
| 打得更快，成绩可信 | true | true | true |
| 没打得更快 | false | true | **true** |
| 这条成绩没被采信 | false | true | **false** |

后两行在 UI 上不该长得一样：前者是「没进步」，后者是「我们没采信你这条」。
一个真实玩家若因口径漂移被持续判不可信，只看 `improved` 永远察觉不到。

---

三条载荷红线（与试炼榜、速度榜一致，测试锁着）：

1. 提交里**没有** `rank`、没有 `verified` —— 客户端连「我是否入榜、第几名」
   都无权自称
2. 榜单只返回 `verified = true` 的行
3. `improved = false` 不是错误，**不要弹失败提示**

## 三、给 UI 的三条口径（都是被数据逼出来的，不是审美偏好）

### 3.1 默认展示玩家打过的最高档，别默认展示晴蓝

低档副本的用时会**成批撞在 200ms 的下界上** —— 满级玩家人人秒杀。
晴蓝榜点开就是一屏 0.2 秒，玩家的第一反应是「这榜坏了」。
真正有竞争的是与自己等级对位的那一档（当前是琥珀，37~41 秒）。

### 3.2 并列按首通更早排，并且要把这条规则告诉玩家

同为 0.2 秒时按首通时刻升序（SQL 索引与 `fetchDungeonBoard` 都已带上
第二排序键）。UI 要写明「用时相同时，更早首通者在前」——
否则并列玩家会以为名次是随机的。这与 docs/51 榜 3
「同关按最早达成排」是同一条口径：**开荒者优先**。

### 3.3 老档没有记录不补记

与 docs/62 §4.1、docs/63 §1.3 一致：没有证据就不能主张。
玩家重打一次就有记录了，成本极低（副本本来就是每日必刷）。

```ts
// 大意，具体位置由接 UI 的人定
const record = game.equipmentDungeon.records[dungeonId];
if (record) {

    dungeonId,
```

**上报顺序有硬要求（深度链）**：同一档必须**按深度升序**上报，
否则第 d 层会被服务端以「还没有上一层的记录」拒收（返回体里带
`clearedDepth`，UI 可以据此提示「先补交第 N 层」）。
换设备或重装的玩家，把本地阶梯从第 1 层依次交上去即可，一次补完。
