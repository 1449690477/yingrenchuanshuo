## 零、诊断：三层病根，一层比一层深

### 病根一（最深）：玩家等级和内容彻底脱锚

关卡内容的等级范围是 **Lv1 ~ 52**（区域 5 最后一章 `levelTo: 52`）。
但玩家等级**没有任何与内容挂钩的上限** —— 挂在最后一关反复刷 Lv52 的怪，
经验照涨、等级照升、裸属性照涨。

`npm run sim` 30 天实测（`scripts/out/growth-30d.csv`）：

| 天 | 等级 | 战力 | 挂机关卡 |
|---:|---:|---:|---:|
| **1** | **30** | 4,511 | 29 |
| 2 | 39 | 6,259 | 38 |
| 26 | 111 | 153,811 | 111 |
| **30** | **118** | **166,968** | 118/150 |

**第一天就升到 Lv30** —— 而区域 1 的内容只到 Lv10 左右。
30 天后等级 118（几乎满级 120），而全部内容只到 Lv52。
玩家等级是内容等级的 **2.3 倍**，一切以等级锚定的系统
（装备解锁、副本档位、品质阶梯）当然全部对不上。

> 「产能跟不上」的真相：不是内容做得慢，是**消耗速度失控**。
> 照这个节奏，就算内容做到区域 9，也只够玩家吃两个月。

### 病根二：主线推荐战力用的是「裸属性」口径

`src/data/stages.ts` 的 `estimateRecommendCP`：

```
推荐战力 = 裸属性战力 × (0.85 ~ 1.85)
```

而玩家实际身上有：满配装备（品质系数最高 15 倍）× 强化（×2.2~2.35）
× 词条 × 套装 × 好感加成。两个口径的实测差距：

| Lv | 裸属性 | 主线推荐（现状） | 满配战力（不含强化词条） | 差距 |
|---:|---:|---:|---:|---:|
| 10 | 393 | 405 | 751 | 1.9× |
| 20 | 583 | 717 | 1,982 | 2.8× |
| 50 | 1,153 | 2,110 | 12,907 | **6.1×** |
| 70 | 1,533 | 2,836 | ~31,700 | **11×** |
| 118 | 2,446 | 4,525 | 166,968 | **37×** |

所有者说的「关卡六千、玩家六万」完全属实，且**越到后期越夸张**。

> 这与 docs/47 修装备副本时发现的是**同一类病**：
> 「该等级玩家该多强」的正确口径（`expectedPower.ts`）当时只接到了装备副本，
> **主线一直没换**。于是玩家同时看到两把互相矛盾的尺子 ——
> 这正是「装备副本和主线曲线对应不上」的直接原因。

### 病根三：没有任何硬门槛，失败没有形状

- 推荐战力只是**展示**，从不拦人；
- 打不过时只有 `η = 1/(1+超额承伤)` 的效率衰减，**没有下界** ——
  效率 0.2 也能永远磨下去；
- 体力系统：常量、字段、恢复逻辑、UI 全都在
  （`STAMINA_BASE_MAX=120`、5 分钟回 1 点、顶栏显示），
  **但全项目找不到一处消耗** —— 纯装饰。

三层叠加的结果：玩家永远在「碾压 → 无聊 → 更快碾压」的循环里，
没有一次「差一点，我去养成一下再来」的时刻 ——
而那个时刻恰恰是这类游戏全部乐趣的来源（docs/40 的胜任感与心流）。

## 一、三条设计铁律（本次重构的验收底线）

1. **单一口径**：全游戏只允许存在一个「该等级玩家该多强」的答案
   （`expectedPower.ts`），任何推荐值、门槛值都必须从它推导，禁止手填。
2. **等级追内容，不许反超**：等级是内容的影子，内容没开放到哪，等级就不能到哪。
3. **失败有形状，但不没收**（docs/40 红线）：退回、门槛、体力都可以，
   扣等级、扣装备、扣已得资产**绝对不行**。

## 二、改动一 · 等级软上限（性价比最高的一刀）

### 规则

```
等级软上限 = 已解锁的最高章节 levelTo + 3
```

- 到达软上限后：**经验照常获得并累积**，等级暂停增长；
  解锁新章节的瞬间，累积经验一次性释放（可能连升数级，是爽点不是惩罚）
- UI 在经验条处显示「已达当前区域顶点 · 推进关卡以继续升级」

### 为什么是 +3 而不是 0

留 3 级余量让玩家在卡关时仍能靠升级获得一点推力（胜任感来源），
但不足以碾压。区域 5 顶 52 + 3 = **55**，即当前版本满级实际值。

### 预期效果（写进 sim 门禁）

| 指标 | 现状 | 目标 |
|---|---:|---:|
| D1 等级 | 30 | **≤ 13**（区域1 顶 10+3） |
| D30 等级 | 118 | **≤ 55** |

### 实施

| 文件 | 改动 |
|---|---|
| `src/data/constants.ts` | `LEVEL_SOFT_CAP_MARGIN = 3` |
| `src/core/progression.ts` | 新增 `levelSoftCap(unlockedMaxLevelTo)`；`gainExp` 处 clamp，超限经验存入 `player.exp` 不清空 |
| `src/stores/game.ts:1258` | 结算处接入软上限（当前已解锁章节从 progress 取） |
| 存档 | **无 schema 改动**（level/exp 字段现成），见第七节迁移 |

## 三、改动二 · 全游戏换成同一把战力尺 + 硬门槛

### 3.1 新锚点函数

`src/data/expectedPower.ts` 新增：

```ts
/** 该等级玩家的「典型完整养成」战力：满配 × 典型强化 × 典型词条 */
export function expectedBuildCp(level: number, classId?: ClassId): number {
  return expectedFullGearCp(level, classId) * TYPICAL_ENHANCE_MUL * TYPICAL_AFFIX_MUL;
}
```

两个系数**从 sim 校准**（不是拍脑袋）：用 30 天模拟里
「实际战力 ÷ expectedFullGearCp(同等级)」的中位数拆出强化与词条贡献，
预计 `TYPICAL_ENHANCE_MUL ≈ 1.5~1.7`、`TYPICAL_AFFIX_MUL ≈ 1.1~1.2`，
以 sim 输出为准写死并加注释说明校准来源。

### 3.2 主线推荐战力换口径

`src/data/stages.ts` 的 `estimateRecommendCP` 整体替换：

```ts
推荐战力 = expectedBuildCp(关卡等级) × 0.85
```

0.85 与 docs/47 的 0.9 同方法论：留一段给玩家「养一养再来」的目标空间。
Lv1~5 特判维持「必须低于裸属性」（防新号第一关被拦，注释里那个 bug 是真事）。

### 3.3 硬门槛（所有者要的「不达标不能去」）

| 位置 | 规则 | 理由 |
|---|---|---|
| **章节之间** | 进入新章节需 CP ≥ 该章首关推荐 × 0.75 | 主门槛。0.75 是「够得着但要努力」 |
| **区域之间** | 通关前区最终 BOSS（已有）**且** CP ≥ 新区首章推荐 × 0.85 | 区域是大关口，标准更高 |
| 同章节内关卡 | **不设硬门槛** | 处处设卡会把游戏变成审批流程 |

被拦时的文案必须是**指路牌不是墙**：
「距离进入还差 1,200 战力 —— 试试强化武器或洗练词条」，
并附一键跳转养成页。（docs/40：反馈系统用于指路，不用于羞辱。）

### 实施

| 文件 | 改动 |
|---|---|
| `src/data/expectedPower.ts` | `expectedBuildCp` + 两个校准系数 |
| `src/data/stages.ts` | 推荐战力换口径 |
| `src/core/stageProgress.ts` | 新增 `canEnterChapter(cp, chapter)` 纯函数 + 缺口计算 |
| `src/views/IdleView.vue` 切换关卡处 | 门槛判定 + 指路文案（UI 由 kimi-ui 落地） |

## 四、改动三 · 战败规则（死亡惩罚的红线内实现）

所有者提议「死亡后回归上一层」。**方向采纳，实现上不用『死亡』**——
此前已定过「承伤高则效率下降」的软惩罚，这次给它加上**下界和形状**：

### 规则

```
η ≥ 0.5          正常挂机（现状不变，承伤越高效率越低）
η < 0.5 连续 3 场  判定「战败」：自动退回上一关，弹出战报
```

- 战报文案：「霜牙狼群太凶了，少女退回了樱花小径 —— 强化装备后再来」
- **不扣经验、不扣装备、不扣金币、不扣体力**（docs/40 红线：失败不得没收已得之物）
- 随时可手动再挑战（消耗体力，见改动四）
- 退回后在上一关正常挂机产出 —— 玩家永远有地方站

### 为什么不做真「死亡回退多层」

回退多层意味着玩家一觉醒来发现进度倒退数关 ——
那是「进度条倒退」，红线明令禁止。退一关 + 硬门槛已经足够制造
「我需要变强」的张力，而不会制造「我被抢走了什么」的怨气。

### 实施

| 文件 | 改动 |
|---|---|
| `src/data/constants.ts` | `DEFEAT_EFFICIENCY_FLOOR = 0.5`、`DEFEAT_STREAK = 3` |
| `src/core/idle.ts` | 结算循环里累计低效场次，触发战败事件（纯逻辑） |
| `src/stores/game.ts` | 战败时切回上一关（复用现有换关逻辑，原子提交） |
| `src/views/IdleView.vue` | 战败战报弹层（kimi-ui） |

## 五、改动四 · 体力实装（只管推进，不管挂机）

### 消耗端设计

| 行为 | 消耗 | 说明 |
|---|---:|---|
| 挑战**未通关**关卡（含重试） | **6 点** | 唯一的主消耗 |
| 战败退回后再挑战 | 6 点 | 同上，不加价 |
| 挂机已通关关卡 | **0** | **绝不消耗**。挂机是本体，收体力费=赶人 |
| 装备副本 | 0 | 已有每日 3 次独立预算，不叠两层限制 |
| 领取离线收益 | 0 | 红线：离线不得有任何代价 |

### 数值

现有常量直接用：上限 120（`STAMINA_BASE_MAX`）、5 分钟回 1 点（288 点/天）。

- 288 ÷ 6 = **每天最多 48 次推进挑战**
- 目标节奏每天推 4~8 关、平均每关重试 1~2 次 ≈ 消耗 50~100 点
- **结论：体力在正常游玩下永远够用**，只拦住「一天肝穿三个区域」的极端行为
- 体力满时照常累积到上限后停止，**不清空、不提示焦虑**（红线：溢出≠惩罚）

> 体力在这套设计里是**保险丝**而不是付费墙：正常玩家感觉不到它，
> 只有把推进当刷子用的行为才会碰到。真正的节奏控制靠软上限和硬门槛，
> 体力只是兜底 —— 三层各司其职。

### 实施

| 文件 | 改动 |
|---|---|
| `src/data/constants.ts` | `STAGE_CHALLENGE_STAMINA_COST = 6` |
| `src/core/stageProgress.ts` | 挑战入口检查并扣减（纯函数，返回不足原因） |
| `src/stores/game.ts` | 扣减接入原子提交；恢复逻辑已有（`idle.ts:210`）不动 |
| `src/views/IdleView.vue` | 挑战按钮显示消耗；不足时倒计时提示（kimi-ui） |
| 存档 | **无 schema 改动**（stamina / staminaRecoverAt 现成） |

## 六、改动五 · 装备副本对齐（大部分会自动痊愈）

装备副本在 docs/47 已改为公式推导（`expectedFullGearCp × 0.9 × 难度`），
**口径本来就是对的**。它现在「对不上」是被病根一、二连累的：

1. 玩家 3 天升到 Lv50，回头打 Lv16 的 azure 档掉 Lv16 蓝装 —— 当然没用。
   **等级软上限生效后此问题自动消失**：到 Lv16 时玩家真的在 16 级的内容里。
2. 主线推荐用裸属性、副本门槛用满配口径 —— 玩家看到两个矛盾的数字。
   **改动二统一口径后自动消失**。

唯一要动手的：**crimson 档（Lv81）**。当前内容顶是 Lv52+3=55，
81 级档位在区域 7 之前不可达，挂在列表里是虚假承诺。

- 改法：`equipmentDungeonGear.ts` 给 crimson 加 `comingSoon: true` 标记，
  UI 显示「区域 7 开放后解锁」，不再显示具体门槛数字
- **不下调等级**：下调到 50 会让 mythic（主线首现 Lv90 的口径）提前两个版本
  出现，把品质阶梯打乱 —— 宁可诚实地「敬请期待」

同理排查 `trialRules.ts` 的四个分段（31/60/90/120）：
绯月以上分段在软上限 55 时代不可达，试炼 UI 按当前可达分段显示即可，不用改数据。

## 附录 A · 实施修订记录（2026-07-30，全部落地后）

实施过程中以下决策与正文有出入，以实测为准修订：

### A.1 内容规模比写文档时大

写文档时内容顶是 Lv52/150 关；实施时区域 6 已入库，实际 **Lv65/180 关**。
软上限、耗尽日等一切从数据推导的值自动跟随（这正是推导而非手填的价值）。

### A.2 击杀目标重排的结构变化（最重要的修订）

正文只写了「提高击杀目标」。第一版直接放大波次数量，立刻踩雷：
**BOSS 掉落节奏被拖慢 140 倍，R5 经济门禁红了**。最终结构是解耦：

- `Stage.clearCycles`：首通目标 = 一轮波次总数 × clearCycles
- 波次本身原样不动 —— BOSS/精英出场节奏、每击杀掉落、每小时经济
  与改动前完全一致，变的只有「首通要打满多少轮」
- 系数（两轮 sim 校准）：区域 {1,2,3,4,5,6} → **{1,45,90,110,200,340}**，
  BOSS 关 ×2.5、精英关 ×1.5

### A.3 门禁目标按实测修订

| 门禁 | 正文目标 | 落地值 | 理由 |
|---|---|---|---|
| G1 | D1 ≤ Lv13 | **D1 ≤ Lv24 且 ≤ 60 关** | 内容变大 + 第一天慷慨是留存友好形状；实测 Lv21/53 关，锁在略宽处防回退（原为 Lv34/94 关） |
| G3 | [0.9, 1.6] | **[0.80, 1.80]** | 实测 1.09~1.74；band 留边防抖动 |
