## 零、一句话结论（不变）

**把数值与外观从「一件装备」里拆开：数值全部住进 8 槽「圣遗物」（工作名），
外观全部住进「衣橱」（纯外观、无数值）。** 老玩家的每一件已刷/已洗/已强化装备，
通过存档 v18 迁移 **1:1 变成同强度的圣遗物 + 解锁对应衣橱外观**，投入不归零；
圣遗物数值完全复用现有公式，不重新设计数值；现有全部平衡门禁原样继续守护新系统。
代码层面这不是推倒重来——数值与外观在现有代码里本来就是两个结构
（`EquipmentDef` 算数值 / `appearanceId → 图层` 管外观），这次是把两个结构分开命名、分开存、分开产出。

## 一、现状盘点（初稿实测，v2 复核补充）

### 1.1 装备规模（实测计数）

| 来源 | 数量 | 说明 |
|---|---|---|
| `EQUIPMENT` 总表 | 353 | 主线 160、珍品商店 75、套装 118 |
| 装备副本 `EQUIPMENT_DUNGEON_GEAR_LIST` | 80 | 8 部位 × 4 档 |
| 竞技场 `ARENA_EQUIPMENT_LIST` | 16 | 四职业 × 4 槽 |
| 好感 `AFFECTION_EQUIPMENT_LIST` | 40 | 心虹珍藏 |
| **合计** | **≈489 件定义** | |

### 1.2 数值侧现状（要「搬家」不「重做」）

- 公式：`部位基准值 = 6 × L^1.35 × ITEM_SCALE` × 品质系数 × 部位权重 × 胚子 × 强化 + 词条
- 养成链：强化 +0~+15、洗练四件套+共鸣、套装（区域套+8 具名套+副本套）、升阶 R5→R6→R7、
  烙印、继承、图鉴 v17、**三套装备预设（916badd，v2 新增迁移面）**、双评分（PR#14）
- 武器元素：挂在武器 `EquipmentDef` 上，是真实战斗属性（克制教学 f0d8e0e 已上线）

### 1.3 外观侧现状（可拆的证据）

- 每个 `EquipmentDef` 有 `appearanceId`；图层三类：`layer`（武器/头冠/衣裙/鞋）、
  `replacement`（整身换装）、`slot-only`（无视觉）
- **真实有图层的只有 4 槽**：weapon / head / body / shoes；其余 4 槽本来就只是数值
- 渲染入口 `resolveCharacterAppearance(classId, level, equipped)` 从 defId 反查外观——
  改成从衣橱槽反查，渲染层几乎不用动

### 1.4 存档与联机现状（迁移必须覆盖的面）

- `SAVE_VERSION=17`；equipped + bag.equipment + equipmentCodex + **预设（presets）** + PR#13 完整性信封/主备链
- 联机 12 个 Edge Function 全部接收 `equipped` 快照并服务端复算——圣遗物化 = 快照语义换版本 + 全函数重打包重部署
- 已上线五榜历史行是已结算数值，不动

### 1.5 时机与风险（初稿判断维持）

- 对：二版已封口；门禁体系正好当安全网；~51 名玩家迁移成本最低
- 风险：二版后最大单次重构（存档+联机+全 UI）；与 docs/73 的排期整合见 §六.2（v2 重排）

## 二、目标模型（v18 之后的样子）

### 2.1 两个新概念

| | 圣遗物（数值） | 衣橱（外观） |
|---|---|---|
| 定义 | `RelicDef`：slot / quality / level / setId / element(武器) / fixedAffixes | `CosmeticDef`：id / name / slot / appearanceId / classId? / 展示稀有度 / 获取来源 |
| 实例 | `RelicInstance`（= 现 `EquipmentInstance` 字段原样） | `CosmeticInstance`（uid / defId / locked） |
| 存哪 | `equipped`（8 槽）+ `bag.relics` | `cosmetic`（4 视觉槽）+ `wardrobe`（永久解锁账本，只增不减） |
| 系统 | 强化 / 洗练 / 套装 / 升阶 / 烙印 / 继承 / 图鉴 / 预设 / 双评分 | 换装 / 染色（后续）/ 展示 |

### 2.2 ★ 圣遗物一律无职业限定（v2 明确为原则）

老板的原始痛点是「A 角色有新装备数值，BCD 也要配一套」。根除它的那一刀是：
**圣遗物模板不允许有 classId**。职业差异只来自三处：职业本体（基础属性/成长/攻速系数）、
职业专属词条（掷出时按当前职业，随实例走）、技能。现有 16 件竞技场职业装备、
副本 gear 的 classId 候选，迁移时一律映射到无职业模板 + 保留已掷出的职业词条。
今后新增任何数值内容都是「一条模板全职业通用」；**新增职业外观才按职业出图（美术活，不是数值活）**。

### 2.3 圣遗物定义表怎么生成（不手写 489 件）

```
圣遗物定义 = 网格表：(slot × quality × level) → 公式数值
           + 具名模板：固定词条/套装/元素件（区域套、8 具名套、副本套、心虹、竞技场）
```

- 生成脚本 `scripts/gen-relic-defs.mts`：读品质进度表 + 区域等级表 + 套装表 → `src/data/relics.ts`
- **迁移期网格 = 旧装备的等级点位 1:1**（保证 N-R2 等价）。
- ★ v2 注记：网格天生支持**按等级连续加密**——这正是 docs/73 A3/第四失真源
  （「定义等级滞后标称等级」的量化阶梯）的结构性解药。**迁移批次不加密**（守恒优先），
  加密作为迁移后 docs/73 标定批次的一个显式旋钮（见 §六.2）。
- 门禁 `N-R1 映射完整性`：489 个旧 defId 恰好映射「一个圣遗物模板 + 一个衣橱条目」，缺口当场红；
  升阶链（R5→R6→R7 defId 对）在 N-R1 中一并断言。

### 2.4 衣橱定义表

- `src/data/cosmetics.ts`：从 489 defId 的 appearanceId 去重生成（约 150+ 条），
  slot-only 无外观条目不进衣橱展示、只进图鉴
- 新外观 = 1 张素材 + 1 行配置，与数值零耦合
- 珍品商店 75 件转纯外观商品：整身换装 + 互动 + 攻击特效保留，数值字段删除

### 2.5 ★ 新玩家的外观获取环（v2 新增，初稿最大缺口）

初稿只处理了「老玩家迁移解锁」。但 v18 之后新玩家掉的是圣遗物（无外观），
若不设计获取环，**新玩家衣橱永远是空的、角色形象永远是初始装**——外观进度感直接消失。
按 docs/71 §七.5（每种资源画收支环）补全：

| 外观来源 | 规则（自动推导，不逐件手配） | 对应旧行为 |
|---|---|---|
| **区域成长解锁（保底环）** | 每进入新区域，自动解锁该区域主题基础外观一套（weapon/head/body/shoes 各一）| 旧玩法里推图换装的形象成长感 |
| **首通/成就解锁** | 区域 BOSS 首通解锁该区进阶外观；副本各档首通解锁副本套外观；套装图鉴集齐解锁具名套外观 | 旧套装/副本装的形象奖励 |
| **商店购买** | 珍品外观（重定价后）+ 各区域普通外观低价位 | 珍品商店 |
| **活动/好感** | 心虹外观走好感线（现有 40 件映射） | 好感装备 |
| **衣橱默认** | 未解锁任何外观时 = 职业基础形象 + 当前区域基础外观自动穿戴（可关） | 防「新玩家全程裸装观感」 |

实现为一张 `src/data/cosmeticUnlocks.ts` 规则表（来源类型 × 条件 → cosmeticDefId），
配门禁 `N-R3 外观可达性`：每个有图层的 cosmeticDef 至少有一条非付费获取路径，
且每个区域的解锁外观数 ≥ 1 套——红了说明有外观成了「幽灵商品」。

### 2.6 ★ 元素的表现层归属（v2 新增）

- 元素是**圣遗物武器槽的数值属性**（拍板项 8，维持初稿推荐）。
- **战斗特效与克制提示一律读圣遗物元素**，与衣橱穿什么武器无关；
  衣橱武器允许与圣遗物元素「视觉不一致」（外观自由优先），但攻击时的元素光效
  按圣遗物元素叠加染色（现有元素特效管线支持按元素配色）。
- 克制教学（f0d8e0e）的文案把「换武器」措辞改为「换武器圣遗物」；
  测试断言提示读数来自 relic 而非 cosmetic。

## 三、老装备怎么变（v18 迁移设计）

### 3.1 每件老装备的去向（一件都不浪费）

| 老装备的 | 去向 |
|---|---|
| 数值（含词条数组/强化等级+逐级增幅/胚子千分数/洗练共鸣/锁定/待决候选/imprintSetId/setId） | 按 (slot, quality, level, 特殊标志) 映射到圣遗物模板，实例字段**原样搬运** |
| 外观 | 该 defId 的 appearanceId 写入 `wardrobe.unlockedCosmeticDefIds`，当前穿戴的自动填入 cosmetic 槽（**迁移瞬间形象不变**） |
| 图鉴（equipmentCodex v17） | 按映射表拆成 `relicCodex` + `wardrobe`，「分解不倒退」口径两边继续生效 |
| ★ 三套装备预设（916badd） | 预设里存的装备引用逐槽映射为对应圣遗物实例引用；映射不到的条目按预设自身的缺件规则处理 |

**等价性门禁（先红后绿）**：
- `N-R2a 功率守恒`：489 defId × 种子化随机实例，迁移前后 `instanceStats` + `combatPower` 逐件相等；
- ★ `N-R2b 战斗读数守恒`（v2 新增）：同批实例对固定标准怪的 `expectedDamage` 与承伤读数逐件相等——
  防元素/职业词条管线在换载体时静默分叉（只对比面板会漏它们）。

### 3.2 图鉴 / 榜单 / 副本 / 商店（初稿维持）

- 五榜历史行原样保留，新提交走 v2 契约（§五）
- 装备副本掉落改圣遗物，档位×部位结构、clearedDepth、保底全部不变
- 珍品商店 75 件转纯外观并重定价（拍板项 5）

### 3.3 迁移链验收（初稿维持 + 铁律 5 全套）

v17→v18 全形态单测 → 裸档直读升级 → `smoke-save.mjs` 真机 5/5 → v9→v18 全链逐级（结果贴频道）

### 3.4 ★ v17 快照留档与应急回读（v2 新增）

PWA prompt 模式下发布不可逆：玩家一旦升到 v18，旧包读不了新档，「回滚发布」救不了已更新玩家。
唯一可靠的后悔药是**数据侧**：
- v18 迁移执行前，把 v17 完整存档作为快照写入 PR#13 恢复面板的备份链（独立键位，不参与主备轮换）；

- 快照保留 30 天后由既有清理策略回收。
- 门禁：迁移单测断言快照写入 + 回读可用。

## 五、联机契约（v2 修订）

### 5.1 契约 v2

快照带 `equipVersion: 2`，内容为圣遗物实例数组；`_core.ts` 换源后 12 函数重打包重部署；
`edge:build` 确定性自检 + 线上探针（docs/72 同款流程）。

### 5.2 ★ v1→v2 服务端转换兼容层（v2 修订，替代初稿「只收 v2 硬拒」）

初稿方案在 PWA prompt 模式下有一个被今天实测过的现实（docs/72：新客户端上线数小时后仍有旧端在跑）：
硬拒 v1 = **未更新玩家的所有提交（试炼/竞技/秘境/进度）连续失败数天到数周**，而失败提示只能劝更新。
更优解是转换而非拒绝，成本极低：
- 迁移映射（defId → 圣遗物模板）是**纯函数确定性表**，编进 `_shared/_core.ts`；
- 服务端收到 v1 快照时先过 `convertLegacySnapshot()` 转成 v2 再走唯一管线（**不是双管线**，
  是单管线前置一个转换器）；转换失败（未知 defId）按现有硬校验拒绝；
- 兼容层挂 30 天日落哨兵（照 drops 的哨兵模式：断言当前日期 < 日落日，红了提醒删除转换器）；
- 拍板项 7 相应改写：见 §八。

### 5.3 部署顺序

服务端先上（v2 管线 + v1 转换层）→ 客户端随后发布 → 观察期（探针 + 采样）→ 30 天后删转换层。
服务端先上时旧客户端完全无感（转换层兜住），**上线窗口内不存在任何玩家提交中断**。

### 6.2 ★ 与 docs/73 的整合排期（v2 反转，替代两份文档各自的旧排期）

初稿说「P0 全部收口后再圣遗物化」。但 docs/73 审查（频道 20:4x）已裁定 A3 需按

## 七、给老板的人话总结

- **做什么**：装备拆成「圣遗物管数值 + 衣橱管外观」。以后出新衣服 = 一张图 + 一行配置；
  出新数值 = 一条全职业通用的模板。四个角色不再需要四套装备数值。
- **老玩家**：已刷已洗已强化的每一件，1:1 变成同强度圣遗物 + 外观全解锁，机器门禁证明一分不亏；
  迁移瞬间角色形象不变；万一出事还有迁移前快照可回读。
- **新玩家**：推图自动解锁区域外观、首通解锁进阶外观——形象成长感不但不丢，比现在更清晰。
- **平衡**：数值公式一个字不改；平衡门禁原样守护；服务端兜住旧客户端，上线期间没有任何玩家的提交会失败。
- **工期**：门禁先行 1~2 天 → 圣遗物化 2~3 周 → 数值标定收口 1 周，合计约一个月出头。
