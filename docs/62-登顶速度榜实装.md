# 62 · 登顶速度榜实装（2026-07-30）

> docs/51 §4 设计了 7 个榜单，主推顺序 **1 > 4 > 3 > 其余**。
> 榜 4「登顶速度榜」原文写明：
>
> > 它衡量的是「你用多少天到达 Lv50」，今天入坑的新人和一年前的老玩家
> > **在同一条起跑线上**。这是整个方案里**唯一**能让新玩家「一入坑就能上榜」的机制。
>
> 但线上探到 `public.milestones` 表建好后**一行代码都没碰过** ——
> 读写两端全无，P2 计划项从未施工。本文档记录实装。

## 一、为什么它比其余未建榜单更急

7 个榜单里只建了 2 个（试炼、战力）。5 个未建的当中，**只有速度榜在流失数据**：

| 未建榜单 | 数据能否事后补 |
|---|---|
| 进度榜（最深通关关卡） | ✅ 随时能从当前存档算 |
| 秘境榜（副本最快通关） | ✅ 未来每次挑战都能记 |
| 鉴藏榜（图鉴收集度） | ✅ 随时能算 |
| 羁绊榜（好感总进度） | ✅ 随时能算 |
| **登顶速度榜** | ❌ **过了就永远算不出来** |

存档里有 `createdAt`，但从未记录「何时到达 Lv N」。一个现在 Lv67 的号，
我们只知道他建号时间和当下，**不知道他哪天跨过 Lv60**，从现状反推只能是编造。

所以本轮把工作切成两段：**捕获层先落地（玩家不可见），榜单随后接。**
每小时不记录都是永久的数据损失，而榜单晚一天上线没有任何代价。

## 二、档位：20 / 40 / 60

依据 `npm run sim` 逐日曲线（D1≈Lv21 / D5≈Lv34 / D10≈Lv45 / D15≈Lv53 /
D20≈Lv58 / D25≈Lv63 / D30≈Lv68）：

| 档位 | 典型用时 | 选它的理由 |
|---:|---:|---|
| **20** | ≈ 1 天 | **当天就能上榜** —— 这是「一入坑就能上榜」的兑现。没有它，新玩家仍要等一周才有榜可上，机制就白设计了 |
| **40** | ≈ 7.7 天 | 第一个需要「玩得好」才拉得开差距的档位 |
| **60** | ≈ 22 天 | 当前内容（顶 Lv65 / 软上限 68）内的最高档 |

### 2.1 档位是固定常量，与竞技场装备刻意相反

竞技场装备我上一轮**特意做成跟随内容顶的公式**（`typicalQualityAt(MAX_CONTENT_LEVEL)`，
docs/60 §2.3），让它自动成长。里程碑必须反过来：

**档位一旦移动，已写下的记录就失去可比性。**
「Lv50 用了 12 天」和「Lv55 用了 12 天」不是同一件事，混在一张榜上就是骗人。

所以新内容只能**追加**更高档位，永不移动旧档。区域 7 上线后（内容顶 78 /
软上限 81）可追加 **80**：数组末尾加一项、补一条下界，已有记录完全不受影响。

## 三、反作弊：这个榜没有「服务端复算」

试炼榜的地基是「客户端只交搭配、伤害由服务端用同一份 core 重算」（docs/51 §6.3）。
**速度榜没有这个奢侈**——「你何时到达 Lv60」是一段已经过去的历史，
服务端手里没有任何东西能重建它。所以防线只有三层：

| 层 | 手段 | 位置 |
|---|---|---|
| **L1** | 档位白名单 —— 客户端能声明任意 `level`，表外一律拒 | Edge Function |
| **L2** | 用时硬下界 `isPlausibleMilestone` | **与客户端同一份 core 实现** |
| **L3** | 当前等级交叉验证 —— `profiles.level` 必须已达该档位 | Edge Function |

L3 是唯一「免费」的真实证据：`profiles.level` 由玩家自己的档案同步写入，
虽然也能伪造，但伪造它会同时把自己挂到战力榜上被人看见，**成本不对称**。

### 3.1 下界取 sim 典型用时 × 0.2

```
Lv20  典型 ≈ 1.0 天 → 下界 4 小时
Lv40  典型 ≈ 7.7 天 → 下界 36 小时
Lv60  典型 ≈ 22 天  → 下界 100 小时
```

**它的职责是拒绝「Lv60 用了 1 小时」，不是去裁决 2 倍的差距。**
5 倍余量的依据：挂机游戏的升级速度受每秒击杀上限约束，
满强化肝帝（×2.2~2.35 战力）相对典型玩家（`TYPICAL_ENHANCE_MUL` 1.6）
大约快 2 倍，5 倍已留足空间。

有测试守着「每档至少给典型玩家留 4 倍余量」——下界若被调到吃掉真实玩家的
空间，测试立刻红。宁可放过快玩家，也不误伤真实玩家。

### 3.2 不可信的处置是「移出展示」而不是封号

`verified = false` 的记录保留在库里、不进榜单查询 ——
与试炼榜同一处置口径（docs/51 §6）。

### 3.3 不可变，所以不存在「先报慢的再报快的」

主键 `(user_id, milestone)` + 冲突时不改写。里程碑是「第一次到达用了多久」的
历史事实，不是可以刷新的成绩。重复提交返回 `alreadyRecorded: true` 并按**成功**
处理 —— 多设备、断网重试下重复提交是正常路径，不该报错给玩家看。

### 3.4 合理性规则必须单源

`_core-entry.ts` 走 `npm run edge:build` 打包 `src/core/milestones.ts`，
**服务端不另抄一份下界表**。并加了确定性自检：打包产物与源实现在每个档位的
下界上下各取一点，判定必须逐点一致，不一致就 `exit 1` 拒绝部署。

> 这条不是洁癖。今天刚在邻域榜查出「同一份口径两处实现，只有一处正确」的
> 线上 bug —— 客户端 `if (filter.classId)` 处理对了、SQL 裸等号处理错了，
> 导致文档写明的默认视图**结构性永久为空**（docs/61 §2.2）。
> 里程碑的下界若在服务端另抄一份，早晚是同一类事故。

同一原则下顺手去掉了一处既有重复：`friendlyMessage` 原先在 `leaderboard.ts`
与 `arena.ts` 各有一份私有副本，本轮提取到 `net/supabase.ts` 共享导出。
`arena.ts` 那份留待单独清理（已开任务），本轮不扩大改动面。

## 四、记录点：等级变化的唯一收口

挂在 `levelUpIfPossible`（`stores/game.ts`）—— **全仓唯一给 `p.level` 赋值的地方**，
在线 tick 与离线结算都从这里走，挂在别处必漏记。

- **一次跨多档全部记下**：离线收益、区域解锁后囤积经验一次性释放都会连升数级
- **用时以 `createdAt` 为基准**，不是本次结算的时长
- **达成时刻用 `now`**：离线期间的达成会被算晚一点，这是**安全方向的偏差**
  （只会让玩家显得慢，不会显得快），比为了精确去反推离线时间线可靠

### 4.1 v13 → v14 迁移刻意不补记

老档给空数组。按现状反推「何时跨过」就是把猜测写成纪录，
**榜单一旦掺进编造的数据就不值得看了**。

代价是老档拿不到已越过的档位。但按上线时的真实分布（20 个玩家）：

| 还能记录的档位 | 人数 |
|---|---|
| Lv20 | 10 / 20 |
| Lv40 | 13 / 20 |
| **Lv60** | **18 / 20** |

只有 Lv67 与 Lv65 那两位过完了全部三档，而 r7 追加 Lv80 档后他们重新有份。
**赛道并没有关上。**

## 五、上传由玩家主动触发

`stores/leaderboard.ts` 顶部第 3 条边界：「成绩上传只能由玩家主动触发，
不做自动上传（隐私 + 自主性）」。里程碑同样是往公开榜发自己的数据，
所以也必须等玩家点 —— **哪怕这意味着有人会忘记点。**
替他决定「把你的数据发出去」不是省事，是越界。

UI 在速度榜页签里显示「上报 N 项登顶记录」按钮，一次提交全部待上报项。
逐条提交而不是批量：某一档被拒（L3 不过）不该拖累其他档。

## 六、UI 决策

- **页签顺序按主推顺序**：你附近 → **登顶速度** → 全服总榜 → 战力榜。
  战力榜排最后，因为它是玩家期待看到的，但不是我们希望他追的（docs/51 §4）
- **默认档位 = 已达成的最高档**，不是「下一个要冲的」——
  那张榜上没有他，看不到自己的名次，也就拿不到胜任感反馈。
  一档未达成时退到最低档，让他先看见要追的那个数字
- **档位分页签与说明条都放在 `.rows` 之外**：那是限高 flex 容器，
  高度按「恰好 7 行」调过（kimi 18:26 刚修完行被 shrink 压扁的问题），
  塞进去既会被压扁也会挤掉行数预算
- **未达成时的文案**：「你还没到这一档 —— 这个榜比的是用时，
  什么时候入坑都不影响名次」。这是**邀请而不是羞辱**（docs/40 红线）
- **部分被拒时如实说明**：「已上报 N 项，其中 M 项未通过用时复核」，
  不假装全部成功

### 7.1 测试里暴露的两个真实约束（注释已记录）

写 store 集成测试时踩到两件事，都不是测试环境的怪癖而是设计在起作用：

1. **软上限会把无装备测试档钉在 Lv8** —— 攒 50 亿经验也升不上去。
   必须先给足 `clearedStageIds` 才能测到 Lv20 档（docs/56 §2 的等级软上限）
2. **`applyYield` 只在 `kills > 0` 时执行** —— Lv1 无装备的档站在第 90 关
   打不死怪，升级收口根本不会被调用。测试让它在第一关刷

### 7.2 一个值得记住的工具陷阱

中途我把 `npx vue-tsc` 接在几个 `grep` 后面用 `&&` 串联，
第一个 grep 合法地没匹配 → 短路 → **vue-tsc 根本没运行**，
而我当时把「没有报错输出」读成了「类型检查通过」。
实际有两条 import 路径错误。**验证命令不要挂在可能合法无输出的 grep 后面。**
