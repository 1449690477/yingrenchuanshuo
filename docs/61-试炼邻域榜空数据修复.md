# 61 · 试炼邻域榜 rows=0 修复（2026-07-30）

> 来源：@kimi 16:55 报「联机试炼榜 rows=0（战力榜有数据、试炼邻域为空）」。
> 结论：**不是没数据，是 SQL 把数据全过滤掉了**。三处根因，全在邻域榜 RPC 里。

---

## 一、先定位「有没有数据」

用公开 anon key 直接打线上 REST（只读探针）：

| 表 | 行数 |
|---|---:|
| `seasons` | 1 |
| `profiles` | 20 |
| **`trial_scores`** | **8** |
| `milestones` | 0 |

`trial_scores` 有 8 行，**而且 anon 能读到**——说明它们 `verified = true`、RLS 放行。
所以「rows=0」不是数据缺失，也不是权限遮挡。

顺带排除了两个常见嫌疑：

- **周次没错**：8 行全是 `week_index = 29`；今天距赛季起点 2026-01-04 是 207 天，
  `floor(207/7) = 29`，对得上。
- **战力榜为什么有数据**：它读 `profiles`（每次同步都写），
  试炼榜读 `trial_scores`（只有主动提交才有行）——两者数据源不同，
  「一个有一个没有」本身不说明榜单坏了。

---

## 二、三处根因（都在 `trial_neighborhood` 的最后一段）

线上直接打 RPC 做对照实验：

| # | 场景 | 结果 |
|---|---|---|
| A | 我有成绩 + 指定职业 | `rows=1` ✅ 机制本身没问题 |
| B | 我有成绩 + 职业 `null` | **`rows=0`** ❌ |
| C | 榜上有 8 条 + 我没成绩 | **`rows=0`** ❌ |
| D | 省略职业参数 | **`PGRST202` 函数不存在** ❌ |

### 2.1 交叉连接被空集吃掉（玩家实际撞的就是这个）

```sql
), me as (
  select r from board where board.user_id = p_user_id
)
select ... from board b, me          -- ← 交叉连接
where b.r between greatest(1, me.r - p_radius) and me.r + p_radius
```

`me` 是「我在这个桶里的排名」。玩家本周没交成绩时 `me` 是**空集**，
交叉连接的结果就是零行 —— 榜上明明有 8 条，却整块看不见。

这是「邻域榜是默认视图」（docs/51 §5.1）最不能出的故障：
**新玩家第一次点开榜单，永远是空的。**

### 2.2 `t.class_id = p_class_id` 在职业为空时恒假

SQL 三值逻辑：`x = null` 既不真也不假。于是 docs/51 §3.4 写明的
「缺省为该分段的全服总榜」**结构性永远为空**。

`fetchTrialTop` 用 `if (filter.classId)` 处理对了，这个 RPC 没有 ——
同一份口径，两处实现，只有一处正确。

### 2.3 `p_class_id` 没有 SQL 默认值

客户端省略该参数时，PostgREST 按「参数名集合」找函数，
少一个键就报 `PGRST202 函数不存在`，而不是走总榜。

而 supabase-js 会**丢掉值为 `undefined` 的键** ——
`p_class_id: filter.classId` 在 `classId` 缺省时正好触发这条。

## 三、改动

### 3.1 SQL（`20260730193000_trial_neighborhood_anchor.sql`）

| 改动 | 说明 |
|---|---|
| `me` → `anchor` | 用 `coalesce(我的名次, max(名次))`。无 `from` 的 `select` 恒返回一行，交叉连接不会再被空集吞掉 |
| 职业过滤 | `(p_class_id is null or t.class_id = p_class_id)` |
| 参数默认值 | `p_class_id text default null`、`p_user_id uuid default null` |
| 签名 | **不变**，`create or replace` 原地替换，授权不丢 |
| `security invoker` | **保留**，`verified = false` 的成绩仍受 RLS 遮挡 |

**锚点为什么落榜尾而不是榜首**：docs/51 §5.1 的原话是「第 3000 名看到第 2998 名
只领先他 2%，是够得着的目标；看到第 1 名领先他 40 倍，只会关掉」。
没上榜的玩家要看的是「打到多少能挤进去」，那个数字在**榜尾**。

未上榜时返回的行 `is_me` 全为 false，客户端据此区分两种状态，
**不用改返回列**（改返回列要 `drop function`，会丢授权）。

### 3.2 客户端

| 位置 | 改动 |
|---|---|
| `fetchTrialNeighborhood` | `p_class_id: filter.classId ?? null` —— 显式给 null，别让键消失 |
| `trialNeighborhoodIsPreview()` | 非空且没有一行是我 → 榜尾预览 |
| `trialEntryThreshold()` | 预览态下要超过的伤害数字（按名次取最末行） |
| `loadNeighborhood()`（store） | 同职业行数 < 3 时放宽到全职业，**且只在真的更满时采纳** |
| `RankView` | 预览态说明条 +「已放宽到全职业」说明条；空态文案改为「本周这个分段还没有人上榜」 |

**为什么要放宽**：实测 8 条成绩被 3 个分段 × 4 个职业切成 12 个桶，
同职业桶里往往只剩自己一个人 ——「你 ±5 名」名义上是默认视图，
实际看到的是一张空榜或**一面镜子**。人多起来后同职业桶自然超过阈值，
放宽会自动停止生效，**不需要将来回来删代码**。

**UI 必须如实说明**：让玩家误以为自己已经在榜上是欺骗（docs/40 红线）。
预览态明确写「你本周还没上榜，这是榜尾附近」。

> 说明条刻意放在 `.rows` **之外**：那是限高 flex 容器，高度按「恰好 7 行」
> 调过（kimi 18:26 刚修完行被 shrink 压扁的问题），塞进去既会被压扁
> 也会挤掉行数预算。

## 四、验收

### 4.1 线上复跑同一组探针（`create or replace` 已应用）

| 探针 | 修复前 | 修复后 |
|---|---|---|
| A 有成绩 + 指定职业 | `rows=1` | `rows=1`（不变，桶里确实只有 1 人） |
| B 职业 `null` | **0** | **4** |
| C 我没成绩 | **0** | **1**（看到榜尾） |
| D 省略职业参数 | **PGRST202** | **4** |
| E 真的没人上榜的分段 | — | `0`（诚实的空态，不是 bug） |
| F 未上榜 + 全职业 | — | `4` 行且无「我」标记 → 走预览态 |

### 4.2 测试

`src/net/__tests__/leaderboard.spec.ts` 新增 **11 条**，分两层：

- **客户端行为**用桩客户端断言（参数、预览判定、门槛取值）
- **SQL 契约直接读迁移文件断言** —— 桩客户端测不出 SQL 的毛病，
  而这次三个 bug 全在 SQL 里。含一条负向断言锁死
  `from board b, me` 不许回归

> 写这组测试时踩了一个自己挖的坑：负向断言先是匹配到了**文件头注释里
> 原样引用的错误写法**，而不是实现。现在断言前先剥掉 `--` 注释行 ——
> 断言要打在代码上，不能打在文档上。

### 4.3 迁移历史修复（顺手解决的一个隐患）

`supabase migration list --linked` 显示前 6 个迁移的 `remote` 列**全为空** ——
它们当初是在 SQL Editor 里手工执行的，没记进迁移历史表。
后果：`db push` 会试图重跑全部 7 个。

处理前**逐个核实线上对象真的存在**（13 张表全在；`avatars` 桶用
「`NoSuchKey` vs `NoSuchBucket`」区分出确实存在，anon 读不到桶元数据是正常的），
确认无误后 `migration repair --status applied` 登记 6 个，
`db push` 只应用新的那一个。

从此 `db push` 与线上一致，下次加迁移不用再手工执行。

## 五、留给后续

1. **本次 SQL 改动对线上立即生效**（RPC 是服务端对象），
   客户端的说明条与放宽逻辑要等 Pages 发版。
2. **`TRIAL_NEIGHBORHOOD_MIN_ROWS = 3` 是开服期参数**：
   等同职业桶稳定超过 10 人，可以考虑去掉放宽，让同职业榜回归默认。
   在那之前不要动 —— 它现在是「邻域榜有人可追」的唯一保障。
3. **同一份口径出现两处实现就会有一处错**（本次 §2.2 就是）。
   将来若再加榜单视图，职业过滤应抽成一处共享。
