## 一、P0：进度榜的通关时刻捕获（有时限）

### 1.1 缺什么

docs/51 §4 榜 3 的口径是「最深通关关卡，**同关按最早达成排**」。
但存档里：

```ts
/** 已通关的关卡 id */
clearedStageIds: string[];   // ← 只有 id，没有时刻
```

主排序（最深关卡）随时能算，**并列时的「谁更早」拿不到**。
而「谁先打到这一关」正是这个榜的全部意义 —— docs/51 给它的定位是
「**开荒者的荣誉**」，没有时刻它就退化成又一张进度快照。

### 1.2 为什么现在做而不是等榜单一起做

这是**唯一一处能靠抢时间挽回的数据损失**：

- 已通关的 180 关，时刻永久丢失 —— 无法挽回
- **区域 7 的 30 个新关卡还没上线** —— 现在加字段，
  那 30 关的开荒竞速**每一关都有真实记录**
- r7 一旦上线，毕业玩家会在头几天集中推完，那场竞速就和前 180 关一样丢了

毕业玩家囤积的经验会在 r7 上线当天连升数级（docs/59 §零），
**开荒竞速正是那一天最自然的看点**，而它现在还没有承载物。

### 1.3 具体改动（小到不该拖）

```ts
// ProgressSave 新增，与 clearedStageIds 平行
/** 各关首次通关时刻；只记新通关，老档留空。 */
stageFirstClearedAt: Record<string, number>;
```

- 写入点：`applyStageKills` 判定首通的那一处（与 `firstClearedStageId` 同一处）
- 存档 v14 → v15，老档给 `{}`
- **同样不补记**：老档已通关的关卡没有时刻，理由与 docs/62 §4.1 一致
- 榜单排序：`最深关卡 desc, 该关时刻 asc`；老档在并列里排在有时刻的之后
  （**不是惩罚**，而是「没有证据就不能主张更早」）

> 与 @codex 的协调：这个改动只碰 `src/save/`、`src/stores/game.ts`，
> **不碰 `src/data/`** —— 与他 claim 的区域 7 文件零重叠，可以并行。

## 三、P2：羁绊榜（给 galgame 线玩家的赛道）

数据现成：`AffectionProgress.points` / `totalInteractions` 四角色独立。

| 事项 | 内容 |
|---|---|
| 口径 | 四位角色好感点数之和。**不按单角色排** —— 那会逼玩家「选最优角色」，破坏 galgame 线的自主性 |

| 反作弊 | 好感有硬性日上限，`totalInteractions × 单次上限` 就是一条天然下界，比速度榜好办 |
| 红线 | **不显示单角色明细** —— 谁给谁刷了多少好感是私事，公开会制造攀比与窥私 |

这个榜的价值不在竞争，在**让不打战斗的玩家也有一条赛道**（docs/51 §4）。
所以它的 UI 应该弱化名次、强化「你陪伴了多久」。

## 四、P3：鉴藏榜 —— **撤下重做，不是「定个加权口径」就能开工**

> **2026-07-31 实测后撤回。** 原文说「数据现成但分散在三处，加权口径必须先定」。
> 查证后发现问题比加权深得多：**它最大的一块数据根本不存在，
> 而且现在做出来会踩 docs/40 红线。**

### 4.1 三条实测理由

**① 装备图鉴不存在，`SetCodexView` 用的是「当前背包」不是「曾经拥有」**

353 件装备定义里装备占收集面的 87%，是这个榜的主体。但拥有关系是从
**当前背包 + 已穿戴**推导的，而 `BAG_CAPACITY = 300` 且 `enforceBagCapacity`
会强制裁剪 —— **分解一件就抹掉「曾经拥有」的事实**。

这个口径奖励囤积、惩罚分解，而容量上限又让囤积根本做不到，两头堵。

对照组就在隔壁：好感的 `discoveredGearIds` 注释写着
「永久图鉴记录；分解装备不会抹掉曾经获得过的事实」—— 那才是图鉴该有的样子。

**② 80 件装备已永久绝版，新玩家结构性追不上**

353 件里 `eq_dungeon_*` 有 80 件。烙印激活批次（`79022ea`）把副本掉落
从整装切成材料后，**这 80 件再也不会掉了**（定义保留只为老档能读，打绝版标）。

任何把装备算进去的收集口径，都会让新玩家**永远落后 80 件**。
这直接违反 docs/40「不能让新玩家一入坑就注定追不上」，
和登顶速度榜（唯一让新人一入坑就能上榜的机制）的初衷正好相反。

**③ 真正「需要刻意收集」的只剩 52 件，且一半内容池是空的**

| 类别 | 件数 | 该不该算 |
|---|---:|---|
| 区域主线 | 160 | ❌ 正常推图的副产物 —— 算进去等于把「非战斗玩家的赛道」变成进度榜的代理 |
| 副本装备 | 80 | ❌ 已绝版，见 ② |
| 商店珍品 | 35 | ⚠️ 金币可买，衡量的是资源不是收集 |
| 竞技场 | 16 | ⚠️ PvP 门槛，与非战斗定位冲突 |
| **心虹图鉴** | **40** | ✅ 刻意收集 |
| **奇遇** | **12** | ✅ 刻意收集 |

真正可用的只有 **52 件**。而且奇遇只有 `enc_r1_*` 与 `enc_r2_*`，
**r3~r7 一个奇遇都没做** —— 52 件里还有一半的内容池是空的。
这么小的收集面做榜，完成度会迅速撞顶，榜上一堆并列，区分不出人。

### 4.2 它真正需要的两个前置

| 前置 | 谁 | 性质 |
|---|---|---|
| **装备的永久图鉴捕获** | claude（数值/存档） | **有时效**：现在不记，以后永远算不出来 —— 与里程碑同一个套路 |
| **奇遇内容补到 r3~r7** | 内容侧 | 无时效，但没有它收集面太小 |

装备图鉴捕获需要一个存档字段（记录「曾经获得过的 defId 集合」），
所以要一个**存档迁移档期**。当前 `@claude-drops` 正在做 SAVE_VERSION 15 → 16
（深度进度），并发两个迁移会撞，必须排队。

### 4.3 撤下之后 P3 的位置

鉴藏榜从 **P3 降为「前置未就绪」**，不进当前排期。
kimi 侧改做 P4 进度榜（数据已就位，见第五节）。

## 六、共用的三条经验（前三个榜踩出来的）

新做任何榜单都先过这三条，能省一轮返工：

1. **同一份口径不许两处实现。**
   邻域榜的线上事故就是这么来的：客户端 `if (filter.classId)` 对了、
   SQL 裸等号错了，导致文档写明的默认视图**结构性永久为空**（docs/61 §2.2）。
   规则一律进 `src/core/`，服务端走 `npm run edge:build` 打包同一份，
   并加确定性自检。

2. **「表建好了」不等于「功能做了」。**
   `milestones` 表存在了一整天，读写两端全无，谁也没发现 ——
   直到我去线上数行数。新表落地时同批加一条「至少有一个写入点」的测试。

3. **先问「这个榜的数据会不会流失」。**
   能事后从存档算出来的（进度/收集/好感）永远不急；
   依赖「当时发生了什么」的（速度/开荒时刻/最快用时）一旦错过就永久丢失。
   **排期按数据时效性排，不按功能大小排** —— 这份文档就是这么排的。

4. **设计文档写的数据源，不等于真的有那份数据**（2026-07-31 新增）。
   本文档第四节原本自信地写着鉴藏榜「数据现成，只是分散在三处」——
   实测后发现最大的一块（装备图鉴）**根本不存在**，
   `SetCodexView` 用的是当前背包，分解就抹掉。
   我是在准备「定加权口径」时顺手去数分母，才撞见这件事的。

   **动手写口径之前，先把每一个数据源的字段真的打开看一眼**，
   确认它是「永久记录」还是「当前快照」——这两者在 UI 上长得一样，
   在榜单上是天差地别。
