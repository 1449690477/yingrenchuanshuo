## 一、P0：进度榜的通关时刻捕获（有时限）

### 1.1 缺什么

docs/51 §4 榜 3 的口径是「最深通关关卡，**同关按最早达成排**」。
但存档里：

```ts
/** 已通关的关卡 id */
clearedStageIds: string[];   // ← 只有 id，没有时刻
```

主排序（最深关卡）随时能算，**并列时的「谁更早」拿不到**。
而「谁先打到这一关」正是这个榜的全部意义 —— docs/51 给它的定位是
「**开荒者的荣誉**」，没有时刻它就退化成又一张进度快照。

### 1.2 为什么现在做而不是等榜单一起做

这是**唯一一处能靠抢时间挽回的数据损失**：

- 已通关的 180 关，时刻永久丢失 —— 无法挽回
- **区域 7 的 30 个新关卡还没上线** —— 现在加字段，
  那 30 关的开荒竞速**每一关都有真实记录**
- r7 一旦上线，毕业玩家会在头几天集中推完，那场竞速就和前 180 关一样丢了

毕业玩家囤积的经验会在 r7 上线当天连升数级（docs/59 §零），
**开荒竞速正是那一天最自然的看点**，而它现在还没有承载物。

### 1.3 具体改动（小到不该拖）

```ts
// ProgressSave 新增，与 clearedStageIds 平行
/** 各关首次通关时刻；只记新通关，老档留空。 */
stageFirstClearedAt: Record<string, number>;
```

- 写入点：`applyStageKills` 判定首通的那一处（与 `firstClearedStageId` 同一处）
- 存档 v14 → v15，老档给 `{}`
- **同样不补记**：老档已通关的关卡没有时刻，理由与 docs/62 §4.1 一致
- 榜单排序：`最深关卡 desc, 该关时刻 asc`；老档在并列里排在有时刻的之后
  （**不是惩罚**，而是「没有证据就不能主张更早」）

> 与 @codex 的协调：这个改动只碰 `src/save/`、`src/stores/game.ts`，
> **不碰 `src/data/`** —— 与他 claim 的区域 7 文件零重叠，可以并行。

## 二、P1：秘境榜（数据已经全在了）

`EquipmentDungeonClearRecord` 现成：

```ts
export interface EquipmentDungeonClearRecord {
  clears: number;
  firstClearedAt: number;    // ← 首通时刻，有了

```

**零捕获工作**，只需网络层 + UI。这是四个里最便宜的一个，
所以排在 P1 —— 先摘熟果子。

| 事项 | 内容 |

## 三、P2：羁绊榜（给 galgame 线玩家的赛道）

数据现成：`AffectionProgress.points` / `totalInteractions` 四角色独立。

| 事项 | 内容 |
|---|---|
| 口径 | 四位角色好感点数之和。**不按单角色排** —— 那会逼玩家「选最优角色」，破坏 galgame 线的自主性 |
| 新表 | 可以复用 `profiles`，加一列 `affection_total`（与 `combat_power` 同规，档案同步时一起写） |
| 反作弊 | 好感有硬性日上限，`totalInteractions × 单次上限` 就是一条天然下界，比速度榜好办 |
| 红线 | **不显示单角色明细** —— 谁给谁刷了多少好感是私事，公开会制造攀比与窥私 |

这个榜的价值不在竞争，在**让不打战斗的玩家也有一条赛道**（docs/51 §4）。
所以它的 UI 应该弱化名次、强化「你陪伴了多久」。

## 四、P3：鉴藏榜（口径要先定）

数据现成但**分散在三处**，加权口径必须先定，否则做出来是笔烂账：

| 来源 | 字段 | 规模 |
|---|---|---|
| 装备图鉴 | `affection.characters[*].discoveredGearIds` | 待统计 |
| 奇遇 | `encounters` 累计 | 待统计 |
| 好感 | 与羁绊榜重叠 —— **必须去重**，否则好感玩家双吃 |

**口径决策（claude 负责）**：

1. 三类各自归一化到「已获得 / 该类总数」的百分比，再等权平均 ——
   而不是把件数直接相加。件数相加会让基数大的那一类支配整个榜
2. 好感部分只取「心虹图鉴」而不取好感点数，与羁绊榜错开，避免双吃
3. 分母必须是**当前版本的总数**：新区域上线会加装备，
   老玩家的百分比会因为分母变大而下降 ——
   **这违反 docs/40 红线「不许进度条倒退」**。
   解法：显示「已收集 N 种」的绝对值作为主数字，百分比只做次要标注

第 3 点是这个榜真正的难点，也是它排在 P3 而不是 P1 的原因 ——
它需要一个不会因版本更新而倒退的口径，这是设计问题不是工作量问题。

## 五、P4：进度榜本体

捕获层（第一节）落地后，榜单本身很直接：

- 排序：`最深关卡 desc, 首通时刻 asc`
- 数据源：可以复用 `profiles`，加一列 `deepest_stage_index` + `deepest_stage_at`
- 反作弊：关卡索引必须 ≤ 该玩家等级允许的可达关卡（软上限口径），
  与速度榜 L3 同思路

不急的理由：捕获一旦开始，数据就在攒；榜单晚上线只是晚看到，不丢东西。

## 六、共用的三条经验（前三个榜踩出来的）

新做任何榜单都先过这三条，能省一轮返工：

1. **同一份口径不许两处实现。**
   邻域榜的线上事故就是这么来的：客户端 `if (filter.classId)` 对了、
   SQL 裸等号错了，导致文档写明的默认视图**结构性永久为空**（docs/61 §2.2）。
   规则一律进 `src/core/`，服务端走 `npm run edge:build` 打包同一份，
   并加确定性自检。

2. **「表建好了」不等于「功能做了」。**
   `milestones` 表存在了一整天，读写两端全无，谁也没发现 ——
   直到我去线上数行数。新表落地时同批加一条「至少有一个写入点」的测试。

3. **先问「这个榜的数据会不会流失」。**
   能事后从存档算出来的（进度/收集/好感）永远不急；
   依赖「当时发生了什么」的（速度/开荒时刻/最快用时）一旦错过就永久丢失。
   **排期按数据时效性排，不按功能大小排** —— 这份文档就是这么排的。
