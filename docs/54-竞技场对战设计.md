# 52 · 竞技场对战设计（玩家互相挑战）

> 所有者需求：玩家可以在排行榜里选一个对手 solo，赢了**拿掉他一部分财产**并
> **顶替他的排名**，让玩家愿意提升、愿意竞争。
>
> 本文档是给实施者（kimi）的完整方案。承接
> [`51-联机排行榜设计方案.md`](51-联机排行榜设计方案.md)，
> 设计透镜与红线沿用 [`40-玩法设计透镜.md`](40-玩法设计透镜.md)。

---

## 零、先给结论：提案的两半，一半照做，一半必须换

| 提案 | 结论 |
|---|---|
| **顶替排名** | ✅ **完全照做**，这是竞技场的核心，本文档围绕它设计 |
| **拿掉对方财产** | ❌ **换成非对称押注**（第二节）—— 换掉之后**更上瘾**，不是更温和 |

第二条不是道德洁癖，是这个品类里被反复验证过的**必死设计**。
下面用具体理由说明，然后给出一个能提供同等甚至更强刺激的替代方案。

---

## 一、为什么「抢夺财产」会杀死放置游戏

### 1.1 挨打的人不在线

放置游戏玩家 95% 的时间是离线的。「被抢」发生时他**根本不在场**。
他下次打开游戏，第一眼看到的是「你损失了 X」。

按峰终法则（doc 40 第二节），**这正好踩在「终」上**，
而 doc 40 对此写得很死：

> ⚠ 反过来也成立：**结束时刻绝不能是负面的**。

一次挂机的「终」本来是「欢迎回来」结算 —— 我们花了很多力气把它做成正反馈。
抢夺机制会把它变成「欢迎回来，你被抢了三次」。

### 1.2 它punish 的是「下线」，不是「失误」

被抢的玩家没有做错任何事，他只是**关掉了游戏**。
用惩罚回应「不玩」，直接击穿麦戈尼格尔的**自愿参与** ——
游戏与苦工的分界线。玩家不会因此更努力上线，只会卸载。

doc 40 红线清单里两条同时被踩：
「失败扣除已获得的东西」「用惩罚代替奖励做驱动」。

### 1.3 死亡螺旋（这条最致命）

```
强者抢弱者 → 弱者更弱 → 弱者退坑 → 次弱变成新的弱者 → 继续被抢 → …
```

这不是推测，是这个机制在真实产品里的固定结局
（Travian、部落冲突早期都靠加护盾和战利品上限才活下来）。
最终结果是**中层玩家整层消失，只剩顶部少数人互殴**，
而顶部玩家很快也会因为没人可打而流失。

### 1.4 它其实并不提供「刺激」

被抢方的情绪是**愤怒和无力**，不是「我要变强」。
抢夺方的情绪也很快钝化 —— 因为**打弱者最划算**，
最优策略是欺负最弱的人，这既没有挑战性也不产生 Fiero。

> **要害在于：刺激来自「我可能失去我押上去的东西」，
> 不是来自「别人失去了他的东西」。**
> 后者只是把成本转嫁给了一个没同意参与的人。

## 二、替代方案：非对称押注

**一句话：挑战者押注，防守方不押。**

| | 挑战者 | 防守方 |
|---|---|---|
| 发起时 | 押上**荣誉印记** | 无感知、无消耗 |
| 挑战者赢 | 拿回押注 + 系统铸造的奖励 + **顶替排名** | 排名下移一位，**资产分毫不损** |
| 挑战者输 | **失去押注** | 排名不变，**额外获得防守奖励** |

### 2.1 为什么这个方案的刺激不减反增

| 你想要的 | 抢夺方案 | 押注方案 |
|---|---|---|
| 真实风险 | 有（但风险在**别人**身上） | **有，且在你自己身上** —— 这才是刺激的来源 |
| 真实决策 | 几乎没有（打最弱的最划算） | **押多少、挑谁**，两个真决策 |
| 打赢强者的爽感 | 有 | **更强**（奖励按对手强度放大，见 4.2） |
| 顶替排名 | 有 | **同样有** |
| 死亡螺旋 | 必然发生 | 不存在 |
| 离线被惩罚 | 是 | **否** |

**关键设计反转：防守成功也有奖励（2.2）。**
于是「被人挑战」从坏消息变成**好消息** —— 这一条把整个焦虑源头掐掉了，
同时不损失任何竞争强度。

### 2.2 防守奖励

防守方每被挑战一次：

- 防守成功：+8 荣誉印记
- 防守失败：+3 荣誉印记（**仍然是正数**）

发放方式：**不实时推送**，统一进每日结算的「防线战报」。
理由：实时推送「有人打你」就是社交攀比式提醒，属 doc 40 禁止项。

> 玩家打开游戏看到的是：「昨天有 6 人挑战你的防线，你守住了 4 次，+38 荣誉」。
> 这是**战绩**，不是**受害通知**。

## 三、核心循环

```
每日 5 次挑战机会（04:00 重置，沿用游戏既有日切）
        ↓
系统给出 3 个候选对手（排名在你上方 1~15 名内随机）
        ↓
选一个 → 选押注档位（10 / 25 / 50 荣誉）
        ↓
服务端复算对决（确定性，见第五节）
        ↓
   赢 → 拿回押注 + 铸造奖励 × 排名差倍率 × 连胜倍率 + 顶替排名
   输 → 失去押注（排名不变）
        ↓
每日 04:00 结算：按段位发荣誉与奖励箱
```

### 3.1 每日次数为什么是 5

- 太少（1~2）：没有「再来一次」的空间，连胜机制形同虚设
- 太多（20+）：变成刷子，单次决策不值钱，且服务端成本上升
- **5 次**：足够形成一轮「试探→调整→冲刺」，也构成一个自然的会话结束点

用完不提示、不催促、不卖次数。**次数用完就是今天玩完了，这是好事**
（doc 40：不玩不应有损失，也不应有「继续玩」的压力）。

### 3.2 三选一，不是全服列表

对照 doc 40 的**选择负担**：全服列表让人瘫痪，3 个候选是可比较的。
每个候选卡片显示：排名、战力、职业、**预估胜率**。

> 预估胜率必须显示。它把「赌」变成「决策」——
> 玩家在权衡「70% 赢小的」还是「35% 赢大的」，这是本设计的乐趣核心。

## 四、数值

### 4.1 押注档位

| 档位 | 押注 | 适合 |
|---|---:|---|
| 试探 | 10 | 挑战比自己强很多的对手 |
| 标准 | 25 | 常规 |
| 全力 | 50 | 高胜率时放大收益 |

### 4.2 胜利奖励公式

```
获得荣誉 = 押注 × 排名差倍率 × 连胜倍率   （押注本身另外退还）
```

**排名差倍率**（对手排名比你高多少）

| 排名差 | 倍率 |
|---|---:|
| 1 – 3 名 | 1.2 |
| 4 – 8 名 | 1.6 |
| 9 – 15 名 | 2.2 |

**连胜倍率**

| 连胜 | 倍率 |
|---|---:|
| 2 连 | 1.2 |
| 3 连 | 1.5 |
| 5 连及以上 | 2.0 |

连胜在**失败时归零**，跨日**保留**（跨日清零会制造「必须一次打完」的压力）。

> 上限校验：50 押注 × 2.2 × 2.0 = **220 荣誉**，是单次最高收益。
> 对照第四节的奖励定价，这个上限不会让顶尖玩家一天之内拉开断层。

### 4.3 段位与掉名

- **精确排名是活的**，会因为别人顶替而下移
- **段位（青樱／绯月／琥珀／绯樱／樱冠）在赛季内只升不降**
- **永远不推送、不动画化排名下降**（doc 40 禁止项）

段位是玩家的「成就」，排名是「当前站位」。前者必须稳，后者可以动。

## 五、对决结算

### 5.1 防守方是离线的

防守方不需要在线。系统保存他**最近一次提交的搭配快照**，
由 AI 按同一套战斗规则驱动。这是异步竞技场的标准做法。

### 5.2 需要新增的 core 函数

现有 `simulateFight(playerStats, monster, rng)` 是「玩家 vs 怪物」，
PvP 需要新的纯函数：

```ts
// src/core/duel.ts —— 必须是纯函数，不得引入网络或存储
export function simulateDuel(
  a: DuelSide,
  b: DuelSide,
  rng: Rng,
): DuelResult;
```

规则建议：

- 双方满血开打
- 按 `spd` 决定行动顺序与行动频率（复用现有战斗规则，不要另起一套）
- **上限 30 回合**；到达上限时按**剩余生命百分比**判胜
- 平局（百分比也相同）判**防守方胜** —— 挑战者需要明确击败对手

上限是必须的：没有它，两个高防低攻的搭配会打不完。

### 5.3 种子与验真

```
seed = hash(attackerId, defenderId, dayKey, attemptIndex)
```

同 doc 51 第六节：**客户端不提交胜负**，只提交「我要挑战谁、押多少」。
Edge Function 取双方快照、跑 `simulateDuel`、自己判定胜负并写库。

由于 `src/core/` 纯净且 RNG 确定性，服务端能用同一份代码复算 ——
**伪造战斗结果不可能**。

### 5.4 战报要能回放

结果返回**逐回合日志**，客户端播成战斗动画。
这是「峰」所在：赢下一场硬仗的过程必须看得见，
只给一个「你赢了」弹窗会浪费掉整个机制的情绪价值。

## 六、复仇机制（最强的回访钩子）

被别人挑战成功后，你获得 **1 次针对该对手的复仇机会**：

- **不消耗每日次数**
- **不需要押注**
- 有效期 24 小时
- 赢了同样顶替排名

为什么这条特别重要：

- 它给了玩家一个**具体的、有名有姓的回来理由**，而不是泛泛的「上线看看」
- 它**零成本** —— 玩家没有因为被挑战而损失任何东西，复仇纯粹是白给的机会
- 它把「我被超越了」的挫败转化为「我有仇要报」的**能动性**

> ⚠ 措辞红线：入口文案写「**反击机会 ×1**」，
> **不得**写「XXX 打败了你，快去报仇」。前者是机会，后者是羞辱。

---

## 七、防滥用

| 风险 | 对策 |
|---|---|
| 定点骚扰某个玩家 | 同一对手**每日只能挑战 1 次**（复仇机会不受此限） |
| 欺负远低于自己的人 | **只能挑战排名在你之上的人**（排名差倍率天然也不鼓励） |
| 小号养大号 | 同 IP／同设备互相挑战不计入排名变动，只标记待审 |
| 刷防守奖励 | 防守奖励每日上限 200 荣誉 |
| 提交伪造搭配 | 同 doc 51 第六节 L1–L4：服务端复算 + schema 校验 + 战力上界 + 账号年龄 |

## 八、数据结构（接 doc 51）

```sql
-- 竞技场排名（每人一行）
create table public.arena_ranks (
  user_id      uuid primary key references public.profiles(id) on delete cascade,
  season_id    text not null references public.seasons(id),
  rank         int  not null,
  tier         text not null,              -- 'qingying' | 'feiyue' | ...
  honor        bigint not null default 0,
  win_streak   int  not null default 0,
  build_snapshot jsonb not null,           -- 防守用搭配，服务端复算的输入
  updated_at   timestamptz not null default now()
);

create index on public.arena_ranks (season_id, rank);

-- 对战记录
create table public.arena_battles (
  id            bigserial primary key,
  attacker_id   uuid not null references public.profiles(id) on delete cascade,
  defender_id   uuid not null references public.profiles(id) on delete cascade,
  day_key       text not null,             -- '2026-07-29'，沿用 04:00 日切
  attempt_index int  not null,
  stake         int  not null,
  attacker_won  boolean not null,
  honor_delta   int  not null,
  rank_before   int  not null,
  rank_after    int  not null,
  battle_log    jsonb not null,            -- 逐回合，供回放
  is_revenge    boolean not null default false,
  created_at    timestamptz not null default now()
);

create index on public.arena_battles (defender_id, day_key);
create index on public.arena_battles (attacker_id, day_key);
```

**RLS**：两张表都只给 `select`（自己相关的行）。
所有写入必须走 Edge Function（service role），客户端无 insert/update 权限。

排名变动必须在**单个 SQL 事务**里完成，否则并发挑战会把排名表写乱。
建议用 `plpgsql` 存储过程做「插入到目标位、区间整体下移一位」。

## 九、每日结算

时间：**每日 04:00**，沿用游戏既有日切（不要另起一套时区逻辑）。

结算内容：

1. **防线战报** —— 昨日被挑战次数、守住几次、获得荣誉
2. **段位奖励** —— 按当前段位发荣誉印记与奖励箱
3. **段位晋升** —— 达标即升，**不降级**

| 段位 | 排名 | 每日荣誉 | 奖励箱 |
|---|---|---:|---|
| 樱冠 | 前 10 | 300 | 圣痕匣 ×2 |
| 绯樱 | 前 100 | 200 | 圣痕匣 ×1 |
| 琥珀 | 前 30% | 120 | 星辉匣 ×2 |
| 绯月 | 前 60% | 80 | 星辉匣 ×1 |
| 青樱 | 其余 | 50 | 星辉匣 ×1 |

**最低档也有奖励**，且金额不算羞辱性的零头 ——
参与就有收获，这是不制造惩罚感的关键。
奖励箱内容与荣誉商店见 [`53-竞技场奖励装备与资源清单.md`](53-竞技场奖励装备与资源清单.md)。

## 十三、一句话总结

> **刺激来自「我押上去的东西可能没了」，不是「别人的东西没了」。**
> 非对称押注保留了顶替排名、保留了真实风险、保留了打赢强者的爽感，
> 但没有制造一个没同意参与的受害者 ——
> 再加上「防守成功也有奖励」，被人挑战从坏消息变成了好消息。
