# 52 · 联机排行榜部署指南（Supabase）

> 实施：kimi。方案：[`51-联机排行榜设计方案.md`](51-联机排行榜设计方案.md)。
> 本文档回答一个问题：**怎么把代码里已经写好的联机排行榜真正开起来。**
>
> 代码在未配置时是纯单机模式：周常试炼、本地成绩簿照常可玩，
> 联机榜静默关闭，游戏主流程完全不受影响（方案 §7 的硬性要求）。

## 二、开通步骤（约 15 分钟）

### 1. 创建 Supabase 项目

到 [supabase.com](https://supabase.com) 建一个免费项目，记下：

- **Project URL**：`https://<ref>.supabase.co`
- **anon public key**（Project Settings → API）

### 2. 开启匿名登录

Dashboard → Authentication → Sign In / Providers → **Anonymous Sign-Ins** 打开。

### 3. 建表

Dashboard → SQL Editor，把
[`supabase/migrations/20260729190000_leaderboard.sql`](../supabase/migrations/20260729190000_leaderboard.sql)
整段粘进去执行一次（或装 CLI 后 `supabase db push`）。

### 4. 部署 Edge Function

```bash
npm install -g supabase          # 或 brew install supabase/tap/supabase
supabase login
supabase link --project-ref <你的项目 ref>

npm run edge:build               # 打包共享 core + 确定性自检（必须做）
supabase functions deploy submit-trial
```

`npm run edge:build` 会生成所有函数的 `_core.ts`，并自动验证「打包产物与
`src/core` 成绩逐点一致」、竞技场对决确定性，以及历史合法词条仍可通过硬校验；
任一自检不过都绝不能部署。

> ⚠ core 代码每次改动后，都要重新 `edge:build`，并统一重部署
> `submit-trial` 与 5 个竞技场函数。只部署其中一个会让试炼与竞技场运行不同的
> `_core` —— 同一件装备可能一边通过、一边报错。

### 5. 配置前端环境变量

本地开发：复制 `.env.example` 为 `.env`，填入第 1 步的 URL 和 anon key，重启 `npm run dev`。

线上（GitHub Pages）：仓库 Settings → Secrets and variables → Actions，
新增 `VITE_SUPABASE_URL` 与 `VITE_SUPABASE_ANON_KEY` 两个 secret，
并在 `.github/workflows/deploy.yml` 的 build 步骤注入：

```yaml
- run: npm run build
  env:
    VITE_SUPABASE_URL: ${{ secrets.VITE_SUPABASE_URL }}
    VITE_SUPABASE_ANON_KEY: ${{ secrets.VITE_SUPABASE_ANON_KEY }}
```

> anon key 是「可以公开」的密钥（安全性由 RLS 保证），但
> **service_role key 永远不能出现在前端代码与仓库里** ——
> 它只存在于 Supabase 服务端，Edge Function 运行时由平台自动注入。

## 三、验收清单（对照方案 §10）

| 检查项 | 验证方法 |
|---|---|
| 客户端不可能提交伤害数字 | `TrialSubmission` 类型无伤害字段；`src/net/__tests__/leaderboard.spec.ts` 运行期再断言一次 |
| 断网 / Supabase 故障不影响主流程 | 断网开游戏 → 挂机一切正常；排行页显示「网络未连接」横幅 |
| 新建账号 3 秒内找到够得着的目标 | 打开排行页 → 默认就是「你附近」，空态文案引导第一次挑战 |
| 「掉名」提示为 0 | 代码里没有名次下降动画 / 被超越推送；环比箭头只在上升时渲染 |
| 排行榜奖励含战力为 0 | 奖励未实装；文案明确「只含称号与外观」 |
| 单机可玩 | 不配置 `.env` → 试炼、成绩簿全部可用 |
| 历史旧装不被误杀 | 用 v9 生成、经 v10 / v11 正式迁移的词条提交试炼与竞技场均成功；把同一值放大 1000 倍后两边均返回 400 |
| PWA 不再半更新 | 发布第二版后，旧版继续完整可用并出现「发现新版本」提示；点击「立即刷新」后入口与懒加载资源切到同一版 |

## 四、后续阶段（未做，按方案 §9）

- **P2**：登顶速度榜（`milestones` 表已建好）、进度榜
- **P3**：鉴藏榜、羁绊榜、赛季称号与头像框发放
- **L5 反作弊**：服务端权威存档（挡住「伪造合法但未获得的装备」，
  目前的 L1–L4 挡不住这个，方案 §6.3 已如实标注）。客户端已有的
  存档信封 / SHA-256 只能发现损坏和低成本直接编辑，攻击者可以重算摘要；
  它不能替代 L5 的服务端资产账本。

## 五、运维注意

- **周一 04:00（北京时间）换周**：Boss 与种子自动轮换，无需任何操作。
- **新赛季**：把 `src/data/trialRules.ts` 的 `TRIAL_SEASON_ID` 递增，
  并在 `seasons` 表插入新行。
- **误标复核**：`trial_scores.verified = false` 的历史行被隐藏但未删除。
  2026-07-30 起不再用平均战力或匿名账号年龄作为拒绝证据；玩家用同一搭配重提、
  服务端复算出同分后会自动恢复为已验证，较低分不会洗白更高旧分。
- **历史词条回归**：反作弊规则调整后，至少用一件 v9→v10→v11 正式迁移的
  装备同时调用 `submit-trial` 与 `arena-snapshot`，再用篡改值确认两边仍返回 400。
- **PWA 发布**：当前使用 `vite-plugin-pwa` 的 `prompt` 更新主流程。新 Service
  Worker 等待玩家点击「立即刷新」后才接管，禁止改回会先清旧缓存的静默
  `autoUpdate`；否则仍在运行的旧入口可能失去它需要的 Supabase 懒加载模块。

## 六、竞技场部署（docs/54 · 已于 2026-07-30 上线）

> 当前生产项目已完成以下三步；本节保留为新项目或重部署时的操作清单。

### 1. 执行两个迁移 SQL

Dashboard → SQL Editor，按顺序各执行一次：

1. [`supabase/migrations/20260730050000_arena.sql`](../supabase/migrations/20260730050000_arena.sql)
   —— `arena_ranks` / `arena_battles` 两表、RLS、`arena_apply_battle` 结算存储过程
2. [`supabase/migrations/20260730060000_arena_grants.sql`](../supabase/migrations/20260730060000_arena_grants.sql)
   —— `arena_grants` 奖励发放表、`arena_apply_settle` / `arena_apply_shop_buy` 存储过程

### 2. 部署 6 个 Edge Function

```bash
npm run edge:build    # 打包全部函数 + 双确定性自检（必须做，自检不过绝不能部署）
supabase functions deploy arena-snapshot
supabase functions deploy arena-candidates
supabase functions deploy arena-challenge
supabase functions deploy arena-daily-settle
supabase functions deploy arena-shop-buy
# submit-trial 若未部署过也一并部署
```

只要共享 `src/core` 有改动，上述 6 个函数必须作为同一个部署批次全部执行，
不能依据“这次只改了试炼 / 竞技场”省略另一侧。

### 3. 配置每日结算 cron（北京 04:10）

`arena-daily-settle` 只接受 service_role 调用（结算防线战报、发奖励、升段位）。
Dashboard → Database → Extensions 开启 `pg_cron` 与 `pg_net`，然后在 SQL Editor 执行：

```sql
select cron.schedule('arena-daily-settle', '10 20 * * *', $$
  select net.http_post(
    url := 'https://<你的项目 ref>.supabase.co/functions/v1/arena-daily-settle',
    headers := jsonb_build_object(
      'Content-Type', 'application/json',
      'Authorization', 'Bearer <service_role key>'
    ),
    body := '{}'::jsonb
  );
$$);
```

> ⚠ `10 20 * * *` 是 UTC 20:10 = 北京时间 04:10（日切后 10 分钟）。
> service_role key 只出现在这一条一次性 SQL 里，执行完不要保存、不要提交进仓库。
> 没有 pg_cron 额度时，也可以用任何外部定时器（GitHub Actions schedule 等）
> 每天 POST 同一个 URL，效果相同。

### 4. 竞技场验收清单

| 检查项 | 验证方法 |
|---|---|
| 未配置时单机不受影响 | 不配 `.env` → 排行页「竞技场」页签显示「尚未开放」，试炼榜正常 |
| 客户端不可能伪造胜负 | `arena-challenge` 用同一份 `src/core` 服务端复算；客户端只传搭配快照与种子 |
| 防守方零成本 | 被挑战不扣任何资源；防线战报是收益（+8 / +3，日上限 200） |
| 无掉名提示 | UI 无「排名下降」文案；被顶替只记为防线战报 + 可选反击机会 |
| 奖励直接进背包 | `arena_grants` 发放即入包，无领取按钮、永不清空 |
| 镜像局公平 | `npm run verify` 的 sim 门禁：8 组镜像对决胜率 45~55% |
